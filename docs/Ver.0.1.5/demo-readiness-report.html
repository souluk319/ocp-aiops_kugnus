RCA ToolPlan 준비 상태

RCA 질문은 Gateway에서 ToolPlan으로 분해된다. 현재 CrashLoopBackOff/Pod restart 계열은 pod_restart_rca로 분류되고, event, pod snapshot, previous log probe, metric probe, RAG runbook evidence를 read-only 근거로 연결한다. 단, 실제 응답에서는 각 evidence를 collected, partial, failed, skipped/missing으로 구분해 보여주며 previous log가 항상 수집된다고 말하지 않는다.

  • ToolPlan schema, task type, read-only invariant, adapter resolution은 scenario evaluator에서 검증된다.
  • runbook_tool은 gateway_rag_runbook_search로 해석되며, Gateway-controlled pgvector/RAG runbook evidence를 RCA 조치 후보와 재발 방지 근거에 연결한다.
  • RcaContext는 collected, failed, missing evidence와 digest/contextId를 포함한다.
  • 답변 UI는 evidence footer, RCA Context JSON, trace id, collected/missing count를 노출한다.

작업 회고: 실제로 겪은 문제와 판단 기준

이 섹션은 단순 회고가 아니라 다음 작업 때 같은 문제를 빨리 식별하기 위한 운영 메모다. 터미널 출력, UI 증상, 검증 결과를 바로 원인 후보로 연결하는 것이 목적이다.

겪은 상황실제 원인/판단다음 기준
빌드와 webpack 반영이 지나치게 느림 repo가 /mnt/c 아래 있을 때 WSL 파일 watcher와 Windows 파일시스템 경계 때문에 rebuild가 느려질 수 있었다. 기본 작업대는 /home/kugnus/cywell/ocp-aiops_kugnus로 둔다. 느려지면 먼저 WSL native path인지 확인한다.
Docker는 켜져 있는데 console bridge가 Docker daemon에 연결하지 못함 Docker Desktop 자체 실행과 WSL integration은 별도다. local console bridge는 WSL 안에서 Docker daemon을 볼 수 있어야 한다. docker version에서 Server 정보까지 나오는지 확인한다. client만 나오면 integration/daemon 문제다.
task fe:dev가 9000 port 사용 중으로 실패함 이전 local console bridge가 살아 있거나 stale 상태였다. 9000/9001/18080/18443은 이미 떠 있으면 WARN일 수 있지만, 새 실행 시에는 충돌 원인이 된다. task kugnus:dev:doctor로 먼저 상태를 본다. WARN은 의도된 기존 서버인지, 낡은 서버인지 구분한다.
UI가 안 바뀌었거나 chunk 404가 발생함 webpack dev server와 console bridge 중 하나만 새 상태라 stale chunk를 물 수 있었다. UI 코드 변경 후 이상하면 plugin dev server 9001과 console bridge 9000를 함께 확인한다. chunk 200과 manifest 200을 본다.
yarn, corepack, node가 상황마다 다르게 잡힘 nvm 기반 Node는 interactive shell에서만 PATH가 잡히는 경우가 있었다. 자동화 스크립트는 필요 시 bash -ic 경로를 사용한다. doctor에서 node/corepack 위치가 /home/kugnus/.nvm/...인지 본다.
웹콘솔 로그인은 되어 있는데 oc 명령은 Unauthorized 브라우저 console session과 CLI oc login session은 별개다. oc whoami, oc whoami --show-server로 CLI context를 따로 확인한다. token/kubeconfig는 commit하지 않는다.
회사 OCP와 로컬 테스트 경계가 헷갈림 현재 시연은 회사 OCP를 read-only 관측 대상으로 쓰는 로컬 WSL 개발 콘솔이다. 회사 OCP에 설치했다고 말하면 안 된다. 시연 표현은 "로컬 콘솔에서 회사 OCP 신호를 읽어 AIOps 흐름을 검증했다"로 고정한다.
RCA 답변이 근거 있는 것처럼 보이지만 실제 evidence가 부족할 수 있음 previous log, event, metric, RAG evidence는 collected/partial/failed/skipped/missing이 섞인다. 증거 상태를 숨기지 않는다. 특히 default namespace에 과거 재시작 Pod 로그가 항상 있다고 말하지 않는다.
Lightspeed 연동을 성공으로 말하고 싶어지는 상황 Gateway가 RCA 보고서를 만들 수 있어도 Lightspeed 최종 stream 성공과는 다르다. OLS body schema 위반은 422를 만들었다. OLS payload는 공식 필드만 보낸다. 현재는 Gateway fallback 가능성을 명시하고, Lightspeed 최종 응답 완전 성공이라고 말하지 않는다.
터미널 PASS만 보고 나중에 무엇을 검증했는지 기억하기 어려움 스크롤 로그는 증거로 약하다. 검증 결과는 JSON/HTML 산출물로 남긴다. UI 검증은 branch/head가 찍힌 ui-verifier-report.json을 보관한다.

남은 제약

  • Lightspeed stream: 현재 화면과 증거에서는 아직 Gateway fallback 경로로 표시될 수 있다. 따라서 “Lightspeed 최종 응답까지 완전 성공”이라고 말하면 안 돼. 네트워크/VPN/회사 LLM endpoint 상태에 따라 runtime 장애가 생기면 UI는 fallback 상태를 표시한다.
  • 실행 무제한: 공식 시연 기본 모드는 execute + approval guard다. unrestricted는 local lab 용도이며 현재 헤더에서 비활성 사유를 표시한다.
  • Host diagnostics: Linux host diagnostics adapter는 gate off 상태다. Windows adapter는 planned 상태다.
  • Cypress/Electron: 기존 Cypress 브라우저 E2E는 WSL OS 의존성 문제 때문에 PASS로 보고하지 않는다. 이번 UI 검증은 Chrome CDP 기반 verifier 결과다.
