## 현재 판단

Memora의 핵심은 "원문을 그대로 임베딩하지 말고, 저장 정보와 검색 표현을 분리하자"는 것이다.

이 개념은 현재 RCA AIOps RAG 시스템에 직접 적용 가치가 있다. 다만 Memora 라이브러리를 바로 production dependency로 넣기보다는, 그 표현 방식을 우리 시스템의 `RCA Memory Card Layer`로 흡수하는 것이 맞다.

현재 우리 시스템은 아래 문제가 먼저 확인되어 있다.

| 항목 | 현재 상태 | 판단 |
| --- | --- | --- |
| Semantic embedding | TEI endpoint 502 | 복구 전 semantic RAG 불가 |
| 저장된 임베딩 | `hashing-bow-v1` fallback | 의미 검색이라고 말하면 안 됨 |
| 코퍼스 | mock PDF + demo runbook 중심 | 실제 운영 런북 부족 |
| 검색 표현 | raw chunk 중심 | 장애 표현 변형에 약함 |
| GraphRAG | 아직 논의 단계 | memory layer 이후가 적절 |

따라서 Ver.0.1.9의 설계 방향은 GraphRAG 전면 도입이 아니라:

```text
TEI 복구
-> 실제 운영 Runbook/SOP/RCA corpus 확보
-> RCA Memory Card Layer 추가
-> Hybrid retrieval 검증
-> OCP resource graph와 연결
-> 필요 시 GraphRAG/GRPO/LoRA 검토
```

이다.

## 기사 원문 핵심 요약

GeekNews 기사와 Microsoft Memora README 기준으로 Memora는 AI agent가 대화와 문서에서 장기 기억을 추출, 저장, 검색하도록 돕는 memory framework다.

중요 개념은 세 가지다.

| 개념 | 의미 | 우리 시스템 해석 |
| --- | --- | --- |
| Memory value | 실제 저장되는 원문 또는 세부 정보. 검색 인덱스에는 직접 넣지 않음. | 원본 runbook, SOP, RCA 보고서, 이벤트 로그, 명령 결과 |
| Primary abstraction | 그 memory가 무엇에 관한 것인지 나타내는 대표 요약. 검색, 병합, 갱신 기준. | "ImagePullBackOff는 이미지 태그, registry 인증, pull secret을 확인한다" 같은 표준 RCA 지식 |
| Cue anchors | 하나의 memory를 찾기 위한 여러 의미 단서. | OOMKilled, ExitCode 137, memory limit exceeded, CrashLoopBackOff 등 |

Memora는 일반 RAG처럼 원문 chunk 전체를 직접 indexing하는 방식에서 벗어나, 검색에는 `Primary abstraction`과 `Cue anchors`를 쓰고, 검색 후 연결된 `Memory value`를 반환한다.

기사에서 소개된 검색 전략은 다음과 같다.

| 검색 전략 | 설명 | 우리 시스템 적용 판단 |
| --- | --- | --- |
| Semantic | vector similarity 기반 검색 | TEI 복구 후 기본 검색 |
| Prompted | LLM이 단계적으로 검색어와 검색 범위를 조정 | RCA 복합 질문에서 유효 |
| Hybrid | semantic + BM25/keyword 결합 | OCP 명령, 에러코드, 리소스명 검색에 필수 |
| GRPO | retrieval policy를 강화학습으로 학습 | 지금은 보류. 데이터/평가 축적 후 검토 |

## 왜 우리 RCA AIOps에 맞는가

OpenShift/OCP 장애 분석은 단순 문서 검색 문제가 아니다.

예를 들어 사용자가 묻는 말은 다음처럼 다양하다.

```text
Pod가 죽었어
OOMKilled가 났어
ExitCode 137이 보여
메모리 초과로 재시작한 것 같아
CrashLoopBackOff인데 원인이 뭐야
```

기존 raw chunk RAG는 문서 안에 같은 단어가 없으면 검색이 흔들린다. 반면 Memory Card는 여러 표현을 `cue_anchors`에 묶을 수 있다.

```json
{
  "primary_abstraction": "Pod OOMKilled 발생 시 container memory limit, node pressure, 최근 배포 변경, application heap 설정을 확인한다.",
  "cue_anchors": [
    "OOMKilled",
    "ExitCode 137",
    "memory limit exceeded",
    "container killed",
    "pod restart",
    "CrashLoopBackOff",
    "메모리 초과",
    "컨테이너 종료"
  ],
  "memory_value_ref": "runbook:ocp-oomkilled#diagnosis"
}
```

이렇게 하면 질문 표현과 문서 표현이 달라도 같은 RCA memory로 접근할 수 있다.

## 제안: RCA Memory Card Layer

Ver.0.1.9에서 제안하는 핵심 시스템 아이디어는 `RCA Memory Card Layer`다.

현재:

```text
Document
-> Chunk
-> Embedding
-> Search
-> Answer
```

제안:

```text
Document / Log / Event / RCA
-> Chunk
-> RCA Memory Card
-> Memory Card retrieval
-> Linked evidence chunk retrieval
-> Tool Plan / RCA JSON / Answer
```

Memory Card는 원문을 대체하지 않는다. 원문으로 가는 검색용 지도를 만든다.

## Memory type 설계

| Type | 의미 | 예시 | 검색 역할 |
| --- | --- | --- | --- |
| factual | 안정적인 구성 사실 | namespace, service owner, route, cluster policy | 환경 맥락 |
| procedural | 반복 가능한 절차 | 배포 절차, 장애 확인 순서, 롤백 절차 | runbook retrieval |
| episodic | 특정 시점의 장애 기록 | 2026-06 특정 OOM 장애 RCA | 유사 사고 검색 |
| policy | 금지/승인/보안 규칙 | delete 금지, patch 승인 필요 | action guardrail |
| topology | 리소스 관계 | route -> service -> deployment -> pod | GraphRAG 연결 |

## RCA 처리 흐름

### 1. 질문 수신

```text
"mockpay 결제 Pod가 계속 재시작하는데 원인 후보와 확인 명령을 알려줘"
```

### 2. Query normalization

```json
{
  "task_type": "openshift_workload_diagnosis",
  "entities": ["mockpay", "pod", "restart"],
  "symptoms": ["pod_restart", "crashloop_possible"],
  "required_evidence": ["pod_status", "events", "logs", "deployment_spec"]
}
```

### 3. Memory Card retrieval

검색 대상:

```text
primary_abstraction
cue_anchors
memory_type
tool_hints
```

예상 검색 결과:

```text
1. OOMKilled diagnosis memory
2. CrashLoopBackOff diagnosis memory
3. Recent deployment rollback memory
```

### 4. Evidence chunk retrieval

Memory Card가 가리키는 원문 chunk와 live OCP evidence를 수집한다.

```text
Runbook chunk
OCP Event
Pod status
Deployment spec
Recent log tail
```

### 5. Tool Plan 생성

```json
{
  "task_type": "openshift_workload_diagnosis",
  "evidenceCollectionSteps": [
    {"tool": "oc_get_pod", "reason": "restart count and phase 확인"},
    {"tool": "oc_describe_pod", "reason": "events와 last state 확인"},
    {"tool": "oc_logs", "reason": "application crash signal 확인"}
  ],
  "mutationAllowed": false
}
```

### 6. RCA JSON 생성

```json
{
  "symptom": "mockpay pod restart observed",
  "cause_candidates": [
    {
      "cause": "memory limit exceeded / OOMKilled",
      "confidence": 0.72,
      "evidence_refs": ["event:oomkilled", "runbook:ocp-oomkilled"]
    }
  ],
  "next_checks": [
    "Pod lastState.terminated.reason 확인",
    "container memory limit/request 확인",
    "최근 배포 변경 확인"
  ],
  "safe_actions": [
    "read-only evidence collection",
    "승인 전 restart/scale/patch 금지"
  ]
}
```

## 현재 시스템에 붙이는 위치

현재 Gateway에는 이미 RAG ingestion/search, Tool Plan, RCA context, `/v1/rca/last` 방향이 있다. Memory Card는 다음 위치에 추가하는 것이 자연스럽다.

```text
komsco-ai-gateway
  ingestion
    document -> chunk
    chunk -> memory_card 후보 생성
  storage
    aiops_rag_documents
    aiops_rag_chunks
    aiops_rag_embeddings
    aiops_memory_cards       [new]
    aiops_memory_card_links  [new]
  retrieval
    query -> memory_card search
    memory_card -> chunk/evidence expansion
  answer planning
    memory_card.tool_hints -> evidenceCollectionSteps
    memory_card.safety_class -> mutation policy
```

## DB 테이블 초안

```sql
CREATE TABLE aiops_memory_cards (
  id uuid PRIMARY KEY,
  memory_type text NOT NULL,
  domain text NOT NULL,
  os_scope text[] NOT NULL DEFAULT '{}',
  primary_abstraction text NOT NULL,
  cue_anchors jsonb NOT NULL DEFAULT '[]',
  evidence_types jsonb NOT NULL DEFAULT '[]',
  tool_hints jsonb NOT NULL DEFAULT '[]',
  safety_class text NOT NULL DEFAULT 'read_only',
  confidence_policy text NOT NULL DEFAULT 'requires_live_evidence',
  source_checksum text NOT NULL,
  embedding_model text NOT NULL,
  embedding vector(1024),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE aiops_memory_card_links (
  id uuid PRIMARY KEY,
  memory_card_id uuid NOT NULL REFERENCES aiops_memory_cards(id),
  target_type text NOT NULL,
  target_id text NOT NULL,
  relation text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

## GraphRAG와의 관계

Memory Card Layer는 GraphRAG의 대체재라기보다 전 단계다.

| 단계 | 역할 |
| --- | --- |
| Chunk RAG | 원문 근거 검색 |
| Memory Card | 장애 표현, 절차, tool hint, evidence type을 정리 |
| GraphRAG | OCP 리소스 관계와 장애 전파 경로 탐색 |
| Policy Engine | 위험 작업 차단 |
| JSON Validator | RCA/Tool Plan 형식 보장 |

GraphRAG는 다음 관계가 안정화된 뒤 붙인다.

```text
Route exposes Service
Service selects Pod
Deployment owns ReplicaSet
ReplicaSet owns Pod
Pod references Secret
Pod mounts ConfigMap/PVC
Event describes Pod
Runbook explains Event
MemoryCard suggests Tool
Evidence verifies CauseCandidate
```

## 파인튜닝 대체 전략

기존 파인튜닝 플랜은 OS별 Tool 선택, Evidence 판단, RCA JSON 생성을 모델에 학습시키는 방향이었다.

Ver.0.1.9에서는 아래처럼 재배치한다.

| 기존 파인튜닝 목표 | 우선 대체 수단 |
| --- | --- |
| OS별 Tool 선택 | Tool Catalog + Memory Card tool_hints |
| Evidence 판단 | evidence_types + live evidence validator |
| RCA JSON 생성 | JSON Schema + structured output + validator |
| Runbook/SOP 지식 | RAG/LLM Wiki/Memory Card |
| 장애 패턴 | episodic/procedural memory |
| 위험 명령 차단 | Policy Engine |
| 지속 개선 | memory card update + failed retrieval set |

파인튜닝은 지금 버릴 것이 아니라 뒤로 보낸다.

나중에 필요한 경우:

```text
- Tool Plan JSON 안정화
- RCA JSON 필드 누락 감소
- 질의 task_type 분류 정확도 개선
- retrieval policy 경량 모델 학습
```

에 제한적으로 사용한다.

## 응용 활용 범위

### 1. OCP 장애 RCA

대상:

```text
CrashLoopBackOff
ImagePullBackOff
OOMKilled
Evicted
Pending
PVC mount failure
Route 접속 실패
Operator degraded
Node pressure
```

활용:

```text
증상 표현 -> Memory Card -> evidence tool plan -> RCA JSON -> 답변
```

### 2. 폐쇄망 설치/교육

Memory Card를 설치/교육 runbook에도 적용한다.

```json
{
  "memory_type": "procedural",
  "primary_abstraction": "폐쇄망 설치 전 이미지 반입, registry, storage class, route 정책, secret을 확인한다.",
  "cue_anchors": ["폐쇄망 설치", "image mirror", "registry", "storage class", "route"],
  "tool_hints": ["oc_whoami", "oc_registry_info", "oc_get_sc", "oc_get_route"],
  "safety_class": "read_only"
}
```

효과:

```text
설치 담당자가 문서 전체를 외우지 않아도,
증상/질문에서 관련 절차와 확인 명령으로 바로 이동할 수 있다.
```

### 3. 발표/시연 방어력

발표 시 단순히 "AI가 답했다"가 아니라:

```text
질문
-> 검색된 Memory Card
-> 연결된 원문 chunk
-> 수집된 live evidence
-> RCA JSON
```

흐름을 보여줄 수 있다.

### 4. 고객별 LLM Wiki

고객 문서, SOP, 장애 이력, 벤더 문서를 Memory Card로 정리하면 고객별 LLM Wiki가 된다.

```text
Customer LLM Wiki
  factual: 서비스/담당자/환경 구성
  procedural: 고객 표준 절차
  episodic: 과거 장애 기록
  policy: 고객 승인/보안 정책
```

### 5. Multi-agent handoff

Memora가 강조하는 shared memory 개념은 우리 시스템에서 agent handoff에 유용하다.

```text
분석 agent
-> Memory Card로 장애 후보와 evidence gap 저장

실행 계획 agent
-> 저장된 Memory Card와 evidence gap을 읽고 Tool Plan 작성

교육/문서 agent
-> 같은 Memory Card를 교육 자료와 FAQ로 변환
```

### 6. 운영 품질 평가

Memory Card 단위로 평가하면 RAG 품질을 더 명확히 측정할 수 있다.

```text
질문이 올바른 Memory Card를 찾았는가
Memory Card가 올바른 원문 chunk를 가리키는가
tool_hints가 안전하고 충분한가
RCA JSON이 evidence_refs를 포함하는가
```

## 최종 판단

Memora 기사에서 가져올 핵심은 프레임워크 자체가 아니라 표현 구조다.

우리 시스템의 다음 설계는 다음 문장으로 고정한다.

```text
RCA AIOps RAG는 원문 chunk 검색만으로 끝내지 않는다.
Runbook, SOP, RCA, OCP evidence를 Memory value로 보존하고,
Primary abstraction과 Cue anchors를 별도 검색 표현으로 만들어,
Tool Plan, Evidence 판단, RCA JSON 생성으로 연결한다.
```
