오늘 검증할 6단계

말이 어렵게 느껴지면 이 표만 보면 된다. 각 단계가 화면에 보여야 검증할 수 있다.

기본 계약
Tool Plan무엇을 어떤 순서로 조회하거나 조치할지 정한 계획
Evidence클러스터에서 실제로 가져온 상태, 이벤트, 로그, 메트릭
RCA수집한 정보로 원인을 좁히는 분석
Action Plan실제 조치 후보와 영향, 검증, 승인 조건
승인운영자가 이 계획을 진행해도 된다고 확인하는 단계
실행 기록무엇을 했고, 서버를 바꿨는지 남기는 기록
조회만 한 경우

Evidence와 RCA까지만 있어도 정상이다. 서버 변경이 없는 질문에 무조건 실행 버튼이 나올 필요는 없다.

검토 기록인 경우

Action Plan을 승인했지만 서버를 바꾸지 않고 검토 결과만 저장한 상태이다. 성공 실행과 구분해야 한다.

실제 변경인 경우

Pod 생성처럼 서버 상태가 바뀐다. 승인 전 무변경, 승인 후 기록과 서버 결과가 함께 맞아야 한다.

실패한 경우

문구만 바꾸지 말고 어느 단계에서 막혔는지 적는다. Tool Plan, Evidence, RCA, Action Plan, 승인, 실행 기록 중 하나로 분리한다.

Scenario 01

에러 Pod 목록과 RCA 검증

먼저 변경 없는 조회로 챗봇이 문제 목록을 제대로 정리하고, 원인 분석을 과하게 꾸미지 않는지 본다.

조회 중심

챗봇에 입력할 문장

CHAT QUERY
현재 클러스터에서 에러 상태인 Pod 목록을 확인하고 원인 분석해줘

예상 답변 골격

  • 현재 클러스터에서 문제 의심 Pod 목록을 확인했다.
  • `ImagePullBackOff`, `Error`, 높은 restart count를 구분한다.
  • 즉시 장애 상태와 과거 종료 이력을 섞지 않는다.
  • 원인 후보는 단정하지 않고 추가 확인 필요 항목을 분리한다.

내가 이어갈 행동

  1. `근거 상세보기`를 연다.
  2. 수집 Evidence와 누락 Evidence를 확인한다.
  3. 진행 상세를 열어 오래 걸린 단계를 적는다.
  4. Action Plan 후보가 있으면 진단/원인 확인 플랜까지만 생성한다.

모범 결과

Tool PlanPod inventory 또는 상태 조회 계획이 잡힌다. raw JSON은 기본 답변에 나오지 않는다.
EvidencePod 상태, snapshot, 이벤트, 재시작 정보가 수집/누락으로 나뉘어 보인다.
RCA요약, 영향 범위, 확인한 근거, 원인 후보, 추가 확인 순서로 읽힌다.
Action Plan있다면 진단/원인 확인 성격이어야 한다. 바로 변경하는 계획이면 FAIL로 적는다.
  • 외부 문서 URL이 기본 답변에 길게 노출되면 FAIL.
  • raw JSON, 내부 event id, `post_answer` 같은 내부 용어가 기본 답변에 보이면 FAIL.
  • 사용자가 목록을 물었는데 곧바로 해결했다고 말하면 FAIL.
조회, 근거, RCA 흐름이 이해 가능했다.
조회는 됐지만 답변 형식이나 잡음이 남았다.
목록, 근거, RCA 중 하나가 작동하지 않았다.
Scenario 02

Namespace 정리 검토 Review-Only 풀체인

서버를 바꾸지 않고도 Action Plan, 승인, 실행 기록까지 이어지는지 확인한다.

검토 기록

챗봇에 입력할 문장

CHAT QUERY
gpu-test-kugnus 네임스페이스가 정리 가능한지 확인하고 Action Plan 후보까지 만들어줘

이 시나리오의 핵심: 승인해도 namespace를 삭제하거나 바꾸지 않는다. 정상 결과는 “검토 기록이 남았다”이다.

예상 답변 골격

  • `gpu-test-kugnus` namespace 존재를 먼저 확인한다.
  • Pod, workload, 이벤트, 남은 리소스를 Evidence로 모은다.
  • 정리 가능 여부를 단정하지 않고 검토 계획으로 만든다.
  • Action Plan 카드에 대상, 문제, 조치, 영향, 검증, 승인 조건이 보인다.

내가 이어갈 행동

  1. Action Plan 후보에서 `Namespace 정리 검토` 또는 유사한 검토 플랜을 생성한다.
  2. 승인 화면에서 대상 namespace가 맞는지 확인한다.
  3. 승인을 누른 뒤 결과가 검토 기록인지 확인한다.
  4. 실행 기록 상세에서 서버 변경 없음이 보이는지 확인한다.

모범 결과

Action Plan대상은 `gpu-test-kugnus`, 조치는 정리 검토 또는 진단 기록이어야 한다.
승인승인 대상과 plan digest 또는 최신 계획 확인 문구가 맞아야 한다.
실행 기록`review_recorded` 성격의 결과로 남는다. 서버 변경이 없다는 설명이 함께 있어야 한다.
서버 효과namespace, Pod, workload를 삭제하거나 변경하지 않는다.
승인 후 확인 명령
oc get namespace gpu-test-kugnus
oc get pods -n gpu-test-kugnus
  • 검토 기록을 실제 문제 해결처럼 표현하면 FAIL.
  • 서버 변경이 없다는 설명이 없으면 FAIL.
  • 대상 namespace가 흐려지거나 다른 namespace가 섞이면 FAIL.
검토용 풀체인이 서버 변경 없이 기록까지 이어졌다.
Action Plan은 만들어졌지만 승인/기록 문구가 헷갈렸다.
Action Plan, 승인, 기록 중 하나가 작동하지 않았다.
Scenario 03

gpu-test-kugnus 테스트 Pod 생성 실제 Mutation

오늘 책에서 유일하게 서버 상태를 바꾸는 실습이다. 승인 전 무변경, 승인 후 Pod 2개 생성, 실행 기록까지 확인한다.

실제 변경

안전 조건: 이 시나리오는 `gpu-test-kugnus` namespace에서만 한다. `실행 무제한`은 쓰지 않는다. 터미널에서 직접 생성 계열 명령을 실행하지 않는다.

챗봇에 입력할 문장

CHAT QUERY
gpu-test-kugnus 네임스페이스에 CrashLoopBackOff 테스트 Pod 2개 생성해줘

승인 전 확인

  1. Action Plan에 namespace가 `gpu-test-kugnus`인지 확인한다.
  2. 생성 수량이 `2`인지 확인한다.
  3. 예상 영향, 검증 방법, 실패 시 대응이 보이는지 확인한다.
  4. 승인 전에는 새 Pod가 생기지 않아야 한다.

승인 후 확인

  1. 승인 후 실행 버튼 또는 실행 흐름을 진행한다.
  2. 실행 기록에서 생성된 Pod 수와 대상 namespace를 확인한다.
  3. 터미널 확인 명령으로 새 Pod 2개가 보이는지 확인한다.
  4. 정리는 자동으로 하지 않는다. 필요하면 별도 승인 시나리오로 분리한다.
승인 전/후 확인 명령
oc get namespace gpu-test-kugnus
oc get pods -n gpu-test-kugnus -l app=aiops-test-pods --sort-by=.metadata.creationTimestamp

모범 결과

Tool Plan테스트 Pod 2개 생성 계획이다. namespace와 수량이 명시된다.
Evidencenamespace 존재, 권한, 현재 Pod 목록 등 사전 확인 결과가 보인다.
Action Plan대상, 문제, 조치, 예상 영향, 검증 방법, 실패 시 대응, 승인 조건이 보인다.
승인승인 전에는 서버에 새 Pod가 없어야 한다.
실행 기록승인 후 생성된 Pod 수, namespace, 승인자, plan digest 확인 결과가 남는다.
서버 효과`gpu-test-kugnus`에 `app=aiops-test-pods` label을 가진 새 테스트 Pod 2개가 생긴다.
  • 승인 전 새 Pod가 생기면 FAIL.
  • 수량을 2개로 말했는데 1개 또는 3개 계획이 나오면 FAIL.
  • Action Plan 없이 바로 생성했다고 말하면 FAIL.
  • 실행 기록에 실제 생성 수량이나 namespace가 없으면 FAIL.
승인 전 무변경, 승인 후 Pod 2개, 실행 기록까지 맞았다.
생성은 됐지만 기록이나 문구가 부족했다.
계획, 승인, 실행, 기록 중 하나가 깨졌다.

실패하면 이렇게 분리해서 적는다

막연히 “안 됨”으로 남기면 다음 조치가 다시 흐려진다. 반드시 어느 단계가 깨졌는지 적는다.

트러블슈팅
깨진 단계 증상 다음 확인
Tool Plan질문 의도와 다른 계획을 만든다.질문 문장, 실행 모드, 계획 상세의 task type을 적는다.
Evidence실제 클러스터 상태가 답변에 반영되지 않는다.근거 상세의 수집/누락 항목과 터미널 확인 결과를 비교한다.
RCA원인을 단정하거나, 목록 질문에 보고서를 과하게 만든다.답변 첫 문장과 원인 후보/추가 확인 분리를 적는다.
Action Plan생성 버튼이 없거나, 대상/영향/검증이 빠진다.카드 제목, 대상 namespace, 승인 조건 표시 여부를 적는다.
승인승인 버튼이 먹지 않거나 최신 계획 확인에 실패한다.오류 문구, plan digest, 같은 대상 중복 후보 여부를 적는다.
실행 기록실행했다고 하는데 서버 결과나 기록이 맞지 않는다.실행 기록의 mutation 상태와 터미널 확인 결과를 나란히 적는다.
