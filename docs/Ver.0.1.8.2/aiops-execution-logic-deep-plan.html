Version 0.1.8.2 Deep Plan

KOMSCO AIOps 실행 로직 심층 계획

이 문서는 가이드문서가 말하는 Tool Plan JSON을 제품 실행 로직으로 해석하고, 현재 구현 상태와 공식 문서 근거를 대조하여 다음 구현 순서를 정리한 산출물이다. 목표는 “챗봇이 말만 하는 상태”가 아니라 “근거를 수집하고, 판단하고, 승인된 조치만 실행하는 AIOps”로 가는 것이다.

한 줄 결론

가이드문서의 핵심은 “LLM이 바로 답변하거나 명령을 실행하는 것”이 아니다. 먼저 ToolPlan을 만들고, 그 계획대로 증거를 수집하고, 그 결과를 RcaContext로 묶은 뒤, 필요한 경우에만 proposal -> sealed plan -> approval -> execute 경로로 넘어가는 것이다.

오늘의 설계 기준은 명확하다. AIOps 기능은 “질문 응답 UI”가 아니라 증거 기반 운영 판단 엔진 + 승인 기반 조치 실행 엔진이다.

가이드문서와 공식 PDF에서 확인한 요구사항

근거 확인한 내용 구현 의미

PDF p2-p4, 가이드문서 37-92행 질문을 OS Context로 분류하고, Tool Plan JSON을 만들고, Evidence 기반 RCA Reasoning을 수행한다. 질문마다 task_type, target, execution_policy, tool_plan이 먼저 생성되어야 한다.
PDF p6, 가이드문서 130행 모델은 운영 명령을 직접 실행하지 않는다. 추상 Tool Plan을 만들고, 실제 실행은 AI Gateway Tool Adapter가 담당한다. event_tool, grep_tool, metric_tool 같은 추상 도구를 OpenShift/Linux/Windows 어댑터가 실제 조회로 바꾼다.
PDF p8-p9, 가이드문서 180-260행 Tool 계획, 증적 수집 범위, 위험도, 신뢰도를 RCA Context JSON으로 구조화한 뒤 Lightspeed에 전달한다. 최종 답변은 “말”이 아니라 ToolPlan + EvidenceRefs + RcaContext를 근거로 생성되어야 한다.
PDF p10, 가이드문서 317행 Operator/OLM 기반 Software Catalog 표준 배포, Channel/Subscription/InstallPlan/CSV 상태 점검이 필요하다. 카탈로그 설치 후 Gateway, Console Plugin, Action Executor, RAG 설정이 CR/Operator 경로로 재현되어야 한다.

공식 문서로 대조한 설계 원칙

분야 공식 근거 우리 설계에 들어가야 하는 규칙
OpenShift Lightspeed Red Hat OpenShift Lightspeed 문서 OLS는 콘솔 안에서 운영 질문에 답하는 공식 경로다. 우리 Gateway는 OLS 앞단에서 사내 RAG, 증거, 감사, 보안 Context를 보강하는 계층이어야 한다.
Console Plugin OpenShift Dynamic Plugins 문서 콘솔 UI는 정식 Dynamic Plugin으로 배포해야 한다. 로컬 개발 서버에서 보이는 화면과 카탈로그 설치 후 화면이 같은 경로로 재현되어야 한다.
OLM 배포 OpenShift Operators/OLM 문서 제품 설치 단위는 CatalogSource, CSV, Subscription, CR이다. 설치 후 수동 포트포워딩이나 로컬 서버 의존 없이 동작해야 한다.
권한 확인 Kubernetes SelfSubjectAccessReview API 사용자 토큰으로 “이 사용자가 이 조치를 할 수 있는가”를 실행 직전에 확인해야 한다. 관리자 토큰으로 몰래 우회하면 안 된다.
메트릭 증거 Prometheus HTTP API 문서 metric_tool은 PromQL instant/range query와 결과 digest를 남겨야 한다. 메트릭이 없으면 “없음”을 근거로 기록해야 한다.
JSON 계약 JSON Schema 공식 가이드 ToolPlan/RcaContext/ActionPlan은 감으로 만든 dict가 아니라 스키마 검증 대상이어야 한다. LLM 출력도 스키마를 통과해야 한다.

목표 실행 로직

이 흐름이 제품의 중심이어야 한다. UI, Gateway, RAG, OLS, Action Executor는 이 흐름을 구현하기 위한 부품이다.

1. 질문 수신 사용자 토큰, namespace, 화면 context, 질문 원문을 받는다.
2. ToolPlan 생성 질문을 분류하고 필요한 도구, 대상, 읽기/실행 정책, 위험도를 JSON으로 고정한다.
3. 증거 수집 Event, Snapshot, Log pattern, Metric, Runbook/RAG를 adapter가 실행하고 evidenceRef를 남긴다.
4. RCA Context 수집된 근거, 빠진 근거, 원인 후보, 신뢰도, 조치 후보를 구조화한다.
5. 답변/조치 OLS/LLM이 RCA를 스트리밍하고, 조치는 승인된 Action Plan 경로로만 실행한다. 
사용자 질문
  -> Auth/Context 수집
  -> ToolPlan JSON 생성 및 스키마 검증
  -> Adapter Resolution
  -> Evidence Runner 실행
  -> RcaContext JSON 생성
  -> Lightspeed 또는 LLM에 Context 전달
  -> RCA 답변 스트리밍
  -> 필요 시 ActionCandidate 생성
  -> ActionProposal
  -> SealedActionPlan + planDigest
  -> ApprovalDecision
  -> 실행 직전 SSAR + evidence freshness 확인
  -> ActionExecutor 실행
  -> Postcondition 검증 + Audit 기록

Action 실행 계약

“AIOps가 실행한다”는 말은 위험하다. 제품에서는 아래 조건을 모두 통과했을 때만 실행이라고 부른다.

단계 생성물 필수 검증 실패 시 표시
조치 후보 ActionCandidate RCA Context의 근거와 연결되어야 함 근거 부족, 대상 불명확
제안 ActionProposal 사용자, 대상, 의도, 위험도 기록 proposal 생성 실패
봉인 계획 SealedActionPlan planDigest 생성, evidence snapshot 연결 digest 없음, evidence 없음
승인 ApprovalDecision 사용자 권한, 만료 시간, planDigest 일치 승인 만료, digest 불일치
실행 ExecutionRecord SSAR, evidence freshness, mutation flag, Action Executor 연결 권한 없음, 근거 오래됨, executor 미연결
사후 확인 PostconditionResult rollout status, pod health, event 감소, alert 변화 실행은 됐지만 정상화 확인 실패

현재 가장 큰 빈칸

빈칸 1 ToolPlan이 스키마 계약이 아님 지금은 Python 함수가 dict를 만든다. 테스트는 있지만 JSON Schema 파일, fixture, schema validation gate가 부족하다.
빈칸 2 Planner와 Adapter가 강하게 결합됨 질문 분류, 도구 선택, 어댑터 매핑이 한 함수에 몰려 있다. 모델 planner를 붙이려면 planner 출력과 adapter resolution을 분리해야 한다.
빈칸 3 Evidence Runner가 계약 중심이 아님 수집 결과가 evidenceRef로 남지만, 각 planned step이 어떤 evidenceRef로 충족됐는지 제품 수준으로 보장해야 한다.
빈칸 4 답변 품질 gate가 약함 OLS/LLM fallback이 발생할 때 이유는 보이지만, “근거 없는 최종 답변 금지”와 “빠진 근거 명시”가 더 강하게 걸려야 한다.
빈칸 5 설치 후 완성 상태 검증 미흡 카탈로그 설치로 Console Plugin, Gateway, Action Executor, Service/Route/Proxy, Secret/ConfigMap이 모두 이어지는지 시나리오 smoke가 필요하다.
빈칸 6 고객 문서/RAG와 조치 로직 연결 미흡 고객 운영 문서가 runbook evidence로 검색되고, 그 근거가 RCA와 action candidate에 붙는지 확인해야 한다.

0.1.8.2 완료 정의

  • ToolPlan, RcaContext, ActionPlan JSON 계약이 문서와 테스트로 고정된다.
  • 대표 RCA 질문에서 ToolPlan이 생성되고, 각 step의 증거 수집 상태가 UI와 API에 보인다.
  • 조치 요청은 직접 실행되지 않고 proposal/plan/approval/execute 단계로만 진행된다.
  • 실행 직전 SSAR, planDigest, approval status, evidence freshness, mutation flag, executor 연결을 모두 확인한다.
  • OLS/LLM/RAG 중 하나가 끊겼을 때 어디가 끊겼는지 화면과 API에 같은 이유로 표시된다.
  • 카탈로그 설치 후 같은 상태가 재현되는 smoke task가 생긴다.

판단

지금 우리가 해야 할 일은 “AIOps 메뉴에 버튼을 더 붙이는 것”이 아니다. 가이드문서가 요구한 실행 로직을 제품 계약으로 고정하는 것이다. 이미 코드에는 ToolPlan, RCA Context, Action Lifecycle의 조각이 있다. 0.1.8.2는 이 조각들을 하나의 실행 경로로 묶고, 검증 가능한 JSON 계약과 smoke test로 고정하는 버전이 되어야 한다.
