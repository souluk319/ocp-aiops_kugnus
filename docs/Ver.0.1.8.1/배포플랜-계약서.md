# Ver.0.1.8.1 배포플랜 계약서

작성 기준일: 2026-06-30 KST  
작업 브랜치: `feat/v.0.1.8`  
기준 HEAD: `06e09c7bd3ad6e592c4bd26f20d0212f8b790be0`

## 1. 목표

회사 OCP 서버 `https://api.ocp.cywell.server:6443`에 Cywell AIOps를 **OperatorHub 카탈로그에서 설치 가능한 제품**으로 배포한다.

이 계약에서 말하는 배포는 CLI로 직접 `Subscription`/`AIOpsInstallation`을 만드는 것이 아니다.

```text
목표 배포 방식:
OCP Console
-> OperatorHub
-> Cywell AIOps
-> Install
-> Operator 설치
-> AIOpsInstallation 생성
-> Gateway / ConsolePlugin / ActionExecutor / Diagnostics 배포
```

즉, 사용자가 OCP 콘솔에서 카탈로그 카드를 보고 설치할 수 있어야 한다.

## 2. 현재 상태

현재 회사 OCP에는 이전 카탈로그 등록 흔적만 있다.

```text
CatalogSource: 있음 (현재 표시명: Cywell AI Kugnus Catalog)
PackageManifest: 있음 (현재 catalog: Cywell AI Kugnus Catalog)
Subscription: 없음
CSV: 없음
AIOpsInstallation: 없음
ConsolePlugin: 없음
Gateway/Plugin/ActionExecutor Pod: 없음
```

따라서 지금 상태는:

```text
이전 제품 카드 노출 단계
실제 제품 runtime 미설치 단계
```

이다.

2026-06-30 현재 로컬 패키징 결과는 다음으로 갱신되어 있다.

```text
CSV: komsco-aiops-kugnus-operator.v0.1.8
CatalogSource displayName: Cywell AIOps Catalog
CSV displayName: Cywell AIOps
Provider: Cywell
RAG embedding: ollama / embeddinggemma:latest / 768
```

따라서 다음 publish는 회사 OCP의 기존 `Cywell AI Kugnus Catalog` 표시를
`Cywell AIOps Catalog`로 갱신하는 작업이다.

## 3. 배포 방식 정의

회사 서버 기준 배포 방식은 두 단계로 나뉜다.

### 3.1 Catalog Publish

명령:

```bash
task kugnus:company:check
task kugnus:company:publish
task kugnus:company:status
```

의미:

```text
서버 확인
이미지 빌드/등록
OLM bundle/catalog 생성
CatalogSource 갱신
PackageManifest 노출
OperatorHub 카드 설치 가능 상태 확인
```

하지 않는 일:

```text
Subscription 생성 안 함
CSV 설치 안 함
AIOpsInstallation 생성 안 함
ConsolePlugin 활성화 안 함
Gateway/ActionExecutor Pod 생성 안 함
```

이 단계가 이번 요청의 핵심이다.

### 3.2 OperatorHub Install

목표 흐름:

```text
OCP Console > OperatorHub > Cywell AIOps > Install
```

설치 후 기대 리소스:

```text
Subscription
CSV
Operator Deployment
AIOpsInstallation
Gateway Deployment
ConsolePlugin Deployment
ActionExecutor Deployment
ConsolePlugin resource
```

직접 실행 명령인 아래는 운영자가 수동 설치를 검증하거나 복구할 때 쓰는 우회 경로다.

```bash
task kugnus:company:install
```

이번 계약의 기본 목표는 위 명령으로 직접 설치하는 것이 아니라, 카탈로그에서 Install 가능한 패키지를 만드는 것이다.

## 3.3 개발과 배포를 반복해서 익히는 기준 루프

앞으로 이 프로젝트는 한 번 배포하고 끝나는 작업이 아니다.
기능을 고치고, 로컬에서 확인하고, 패키지로 만들고, 회사 OCP 카탈로그에 올리는 일을 계속 반복해야 한다.

따라서 매번 아래 세 층을 분리해서 본다.

```text
1. 내 PC 기능 확인
   코드가 실제로 동작하는지 본다.

2. OLM 패키지 확인
   동작하는 코드가 OperatorHub 제품 설치물로 묶였는지 본다.

3. 회사 OCP 반영 확인
   회사 서버 카탈로그와 설치 리소스에 반영됐는지 본다.
```

각 층에서 보는 것이 다르다.

| 층 | 확인 질문 | 대표 명령 | 여기서 실패하면 |
| --- | --- | --- | --- |
| 내 PC 기능 | API/RAG/RCA가 현재 코드로 도는가 | `task kugnus:rag:chat:smoke`, `task kugnus:scenario:verify` | Gateway 코드, `.env`, RAG DB, 홈서버 임베더 확인 |
| OLM 패키지 | 제품 버전과 설치 YAML이 맞는가 | `task kugnus:package` | `scripts/olm-package.py`, `scripts/kugnus-olm.sh`, generated YAML 확인 |
| 회사 카탈로그 | OperatorHub에 새 제품 카드가 보이는가 | `task kugnus:company:check`, `task kugnus:company:publish`, `task kugnus:company:status` | `oc whoami --show-server`, CatalogSource, PackageManifest 확인 |
| 회사 설치 | 설치 후 runtime이 뜨는가 | OperatorHub Install 또는 승인 후 `task kugnus:company:install` | Subscription, CSV, AIOpsInstallation, Deployment, Pod 확인 |

개발할 때 매번 외워야 하는 흐름은 아래 하나다.

```text
코드 수정
-> 로컬 기능 smoke
-> task kugnus:package
-> generated YAML 확인
-> task kugnus:company:check
-> task kugnus:company:publish
-> task kugnus:company:status
-> OCP Console OperatorHub에서 Install 확인
-> 필요하면 AIOpsInstallation 생성/수정
-> runtime 상태 확인
```

중요한 기준:

```text
로컬 smoke가 실패하면 배포하지 않는다.
task kugnus:package가 실패하면 배포하지 않는다.
회사 서버가 https://api.ocp.cywell.server:6443 이 아니면 배포하지 않는다.
OperatorHub 카드에 개인 실험명이 보이면 배포하지 않는다.
EmbeddingGemma 768 설정이 generated AIOpsInstallation에 없으면 배포하지 않는다.
```

이 루프를 익히면 "어디가 문제인지"를 아래처럼 바로 나눌 수 있다.

```text
로컬 smoke 실패:
  아직 제품 코드 문제다.

package 실패:
  제품화 포장 문제다.

company:publish 실패:
  회사 OCP 카탈로그 반영 문제다.

OperatorHub Install 실패:
  OLM 설치/권한/이미지 문제다.

runtime Pod 실패:
  Operator가 만든 실제 Gateway/ConsolePlugin/ActionExecutor 문제다.
```

## 3.4 OpenShift binary build 업로드 제외 기준

회사 publish는 OpenShift binary build를 쓰기 때문에, 내 PC의 빌드 컨텍스트를 tar로 묶어 회사 서버에 올린다.
이때 실행에 필요 없는 로컬 산출물은 올리지 않는다.

제외 위치:

```text
scripts/kugnus-olm.sh
  -> prepare_build_context()
    -> tar --exclude=...
```

현재 제외 대상:

```text
node_modules, dist, .venv
.cache, .pytest_cache, .ruff_cache, .mypy_cache
coverage, htmlcov, playwright-report, test-results
integration-tests screenshots/videos/downloads/results/reports
cypress screenshots/videos/downloads
.env, .env.*
*.pyc, *.pyo, *.pyd, *.log, *.pid, *.tmp
```

남기는 대상:

```text
Dockerfile
package.json / yarn.lock / .yarn/releases
requirements.txt
실제 Gateway/ConsolePlugin 소스
```

이 기준은 업로드 속도와 보안 둘 다를 위한 것이다.
특히 `.env`와 `.env.*`는 토큰이 섞일 수 있으므로 회사 서버 build context에 올리지 않는다.

## 4. 조치 실행 모드 계약

요구사항은 read-only만이 아니라 조치 실행까지 가능한 설치다.

허용 목표:

```text
mode = execute
capabilities.mutations = true
capabilities.unrestrictedCommands = false
```

금지 목표:

```text
mode = unrestricted
arbitrary shell exec
임의 patch/delete/apply
namespace/PVC/Secret 삭제
cluster-wide 설정 변경
```

초기 실행 허용 action은 typed action allowlist로 제한한다.

```text
허용 후보:
- Deployment rollout restart
- Deployment bounded scale
- Deployment rollback
- HPA min/max bound change
- controller-owned unhealthy pod eviction

금지 후보:
- delete namespace
- delete pvc
- secret 수정
- arbitrary yaml patch
- node drain/cordon
- host shell command
```

## 6. 결정해야 할 설치 UX

OperatorHub 설치 UX는 둘 중 하나로 결정해야 한다.

### 방식 A: Operator만 설치, CR은 사용자가 생성

흐름:

```text
OperatorHub Install
-> Subscription/CSV/Operator만 설치
-> 사용자가 AIOpsInstallation CR 생성
-> runtime 배포
```

장점:

```text
안전함
설치자가 mode/read-only/execute를 선택 가능
운영 변경이 명시적
```

단점:

```text
Install 클릭 한 번으로 제품이 바로 뜨지는 않음
교육/설치 문서가 필요함
```

### 방식 B: OperatorHub Install 후 runtime 자동 생성

흐름:

```text
OperatorHub Install
-> Operator 설치
-> 기본 AIOpsInstallation 자동 생성
-> Gateway/ConsolePlugin/ActionExecutor 자동 배포
```

장점:

```text
사용자 경험이 단순함
카탈로그에서 설치하면 바로 제품이 뜸
```

단점:

```text
운영 변경 범위가 커짐
execute mode일 경우 승인/정책 검토가 더 중요함
잘못 설정하면 설치 즉시 runtime이 뜸
```

Ver.0.1.8.1 권장안:

```text
방식 A를 기본으로 한다.
단, 설치 시연/교육용으로 방식 B를 별도 승인 플래그에서만 허용한다.
```

## 7. 구현 변경 계약

### 7.1 Catalog metadata

OperatorHub에 보이는 제품 문구는 개인 실험명 없이 회사 제품명으로 보인다.

```text
CatalogSource displayName: Cywell AIOps Catalog
CSV displayName: Cywell AIOps
Provider: Cywell
Visible description/link label: kugnus 없음
```

검증:

```bash
task kugnus:package
python3 - <<'PY'
import json
from pathlib import Path

csv = json.loads(Path("olm/generated/bundle/manifests/komsco-aiops-kugnus-operator.v0.1.8.clusterserviceversion.yaml").read_text())
catalog = json.loads(Path("olm/generated/catalog/01-catalogsource.yaml").read_text())
visible = "\n".join([
    catalog["spec"]["displayName"],
    catalog["spec"]["publisher"],
    csv["spec"]["displayName"],
    csv["spec"]["provider"]["name"],
    csv["metadata"]["annotations"].get("description", ""),
    csv["spec"].get("description", ""),
]).lower()
print(catalog["spec"]["displayName"])
print(csv["spec"]["displayName"])
print(csv["spec"]["provider"]["name"])
assert "kugnus" not in visible
PY
```

PASS:

```text
Cywell AIOps Catalog
Cywell AIOps
Cywell
```

공식 repository URL이 정해지기 전에는 CSV repository/link를 기본값으로 넣지 않는다.
개인 fork URL이 OperatorHub 카드에 노출되는 것을 막기 위해서다.

### 7.2 Execute mode package

기본 package는 read-only를 유지한다.

execute catalog package는 아래 승인값이 있을 때만 생성한다.

```bash
KOMSCO_AIOPS_MODE=execute
KOMSCO_AIOPS_ENABLE_MUTATIONS=true
KOMSCO_AIOPS_ENABLE_UNRESTRICTED_COMMANDS=false
```

검증 조건:

```text
mode == execute
capabilities.mutations == true
capabilities.unrestrictedCommands == false
ActionExecutorReady readiness condition 포함
KOMSCO_AI_ENABLE_MUTATIONS=true
KOMSCO_AI_ENABLE_UNRESTRICTED_COMMANDS=false
```

### 7.3 Bootstrap policy

기본:

```text
KOMSCO_AI_OPERATOR_BOOTSTRAP_INSTALLATION=false
```

즉 OperatorHub Install 후 `AIOpsInstallation`은 사용자가 생성한다.

자동 runtime 설치를 원하면 별도 승인 플래그가 필요하다.

```text
KOMSCO_AI_OPERATOR_BOOTSTRAP_INSTALLATION=true
```

단, execute mode와 bootstrap을 동시에 켜는 것은 운영 변경이므로 별도 승인 대상으로 둔다.

## 13. 선임 보고용 한 문장

```text
이번 배포는 CLI로 직접 설치하는 방식이 아니라, 회사 OCP OperatorHub에서 Cywell AIOps를 Install 가능한 카탈로그 패키지로 갱신하는 작업입니다. 현재 카탈로그 표시명은 Cywell AIOps Catalog / Cywell AIOps / Cywell 제공으로 고정했고, 다음 단계는 package check 통과본을 company:publish로 반영한 뒤 OCP Console에서 Install 흐름을 검증하는 것입니다. 조치 실행은 unrestricted가 아니라 execute + mutations=true + unrestricted=false + 승인 기반 typed action으로 제한해 열겠습니다.
```
