v0.2.8.1 Local Test Incident Report

5174 연결 실패는 회사 서버 문제가 아니라, 로컬 테스트 경로가 둘로 갈라진 문제였다.

이 문서는 “자동 테스트는 통과했는데 사용자가 5174를 열면 왜 또 연결 끊김이 나왔는가”를 남기는 원인 보고서이다. 결론부터 말하면, WSL 내부 검증과 Windows 브라우저 검증을 같은 것으로 착각한 것이 1차 실패였다.

현재 결론

자동 verifier는 CDP network intercept로 통과했지만, 사용자가 직접 여는 5174 포털은 Vite proxy와 Gateway 포트 상태에 의존하고 있었다. 그래서 “자동 테스트 통과”가 “수동 테스트 가능”을 보장하지 못했다.

최종 수정

5174 하나에서 정적 포털 화면과 local fixture `/v1/*` API를 같이 서빙하도록 바꿨다. 이제 `http://localhost:5174/dashboards/aiops`는 별도 18080 Gateway나 Vite proxy 없이 로컬 테스트 화면과 API를 함께 제공한다.

문제 계층

  1. 01
    5174 웹 서버와 Gateway API는 같은 것이 아니었다.

    `/dashboards/aiops`가 200이어도 `/v1/cluster/summary`가 500이면 포털은 “게이트웨이 연결 확인 필요”로 보인다.

  2. 02
    기존 portal dev server는 `/v1/*`를 18080으로 proxy한다.

    `komsco-ai-portal/vite.config.ts`의 기본값은 `http://127.0.0.1:18080`이었다. 18080이 없으면 5174는 화면만 뜨고 API는 실패한다.

  3. 03
    WSL 내부 성공과 Windows 브라우저 성공은 다르다.

    WSL 안에서 `curl`이 성공해도, Windows 브라우저가 여는 `localhost:5174`가 같은 프로세스를 본다는 보장은 없었다.

  4. 04
    Vite 재시작은 Node 버전 때문에 실패했다.

    WSL 기본 Node는 `v18.19.1`이었고, portal의 Vite는 Node 20.19+를 요구했다. 로그에는 `crypto.hash is not a function`이 남았다.

  5. 05
    최종 해결은 “서버 둘”이 아니라 “5174 단일 서버”였다.

    정적 포털과 fixture API를 한 프로세스에서 서빙해서 proxy, Node/Vite dev runtime, WSL/Windows port forwarding 변수를 줄였다.

내가 잘못 판단한 지점

잘못된 판단 왜 문제였나 앞으로의 기준
WSL `curl 200`이면 사용자도 된다고 판단 사용자는 Windows 브라우저에서 `localhost`를 연다. 네트워크 경로가 달랐다. 로컬 UI는 반드시 Windows `curl.exe`와 실제 브라우저 DOM까지 확인한다.
`5174` 페이지 200만 확인 페이지는 떠도 `/v1/*` API가 500이면 포털은 연결 실패 상태다. `/healthz`, `/v1/cluster/summary`, `/dashboards/aiops` 세 개를 같이 본다.
Vite dev server를 계속 재시작하려 함 Node 18/Vite 7 런타임 mismatch 때문에 재시작 자체가 실패했다. 수동 테스트용은 dev server보다 단일 fixture server를 우선한다.
자동 테스트 통과를 수동 테스트 준비 완료로 표현 자동 테스트는 CDP intercept 환경이라 사용자의 수동 브라우저와 조건이 달랐다. 자동 테스트 통과와 수동 테스트 가능은 별도 acceptance criteria로 둔다.
