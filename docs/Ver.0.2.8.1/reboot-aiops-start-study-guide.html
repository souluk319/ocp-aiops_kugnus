재부팅이 무서운 상태를 끝내기 위한 문서

재부팅 후 Kugnus AIOps를 다시 켜는 법

이 문서는 “무슨 명령을 치면 되는가”에서 멈추지 않는다. 짧은 명령이 Taskfile.yml의 어떤 블록을 타고, 어떤 스크립트를 실행하며, 내 PC와 회사 OpenShift 서버 중 어디를 건드리는지까지 같이 본다.

로컬 실행 기준 회사 서버 설치 아님 oc 로그인 필요 Windows 브라우저 확인 포함

1. 재부팅 후 첫 실행

재부팅 후에는 아래 순서만 먼저 한다. 첫 번째 명령은 필요한 로컬 구성요소를 켜고, 두 번째 명령은 연결 상태를 판정한다.

Ubuntu/WSL 터미널에서 실행 
cd /home/kugnus/cywell/ocp-aiops_kugnus
task kugnus:aiops:up
task kugnus:dev:doctor

정상 기준은 task kugnus:dev:doctor 마지막에 Doctor result: PASS가 나오는 것이다. 현재 코드 기준으로는 PASS=40 WARN=0 FAIL=0이 기대값이다. 나중에 검사 항목 수가 바뀌면 핵심 기준은 FAIL=0이다.

브라우저에서 확인

Windows Chrome 또는 Edge에서 아래 주소를 연다.

http://localhost:9000/dashboards/aiops

9000은 로컬 OKD 콘솔 브릿지다. 회사 서버에 AIOps를 설치한 주소가 아니다.

oc 로그인이 만료되어 있으면

task kugnus:aiops:up이 실패할 수 있다. 이때는 회사 OpenShift 로그인만 새로 하고 같은 명령을 다시 실행한다.

토큰 만료 시 
oc login https://api.ocp.cywell.server:6443
task kugnus:aiops:up
task kugnus:dev:doctor

2. 원래 정상 구조

정상은 “내 PC에서 뭐가 잔뜩 떠 있다”가 아니다. 정상은 목적에 따라 로컬 개발, 시나리오 테스트, 회사 서버 배포가 분리되어 있는 것이다.

구분 무엇을 하는가 회사 서버에 만드는 것 주로 쓰는 명령
로컬 개발 내 PC에서 Gateway, 콘솔 플러그인, 로컬 콘솔 브릿지를 띄우고 회사 OpenShift 일부를 읽는다. 설치 리소스는 만들지 않는다. 다만 oc port-forward로 기존 서비스를 연결한다. task kugnus:aiops:up, task kugnus:dev:doctor
시나리오 테스트 격리된 테스트 namespace에 테스트 pod나 장애 조건을 만들고 AIOps가 감지/설명하는지 본다. 테스트 namespace 안에만 pod, event, config 같은 실험물을 만든다. 현재는 테스트 namespace 권한/정책을 먼저 확정해야 한다.
회사 서버 배포 OperatorHub 카탈로그, Subscription, Operator, AIOpsInstallation을 통해 실제 운영 형태로 올린다. 카탈로그, 설치 객체, gateway/plugin/executor/diagnostics operand를 만든다. task aiops:company:check, publish, install, status
왜 로컬이 복잡해 보이나

배포 환경에서는 OpenShift가 Service, Route, Pod, ServiceAccount, ConsolePlugin 연결을 안쪽에서 관리한다. 로컬 개발에서는 그 안쪽 연결을 내 PC에서 임시로 흉내내야 하므로 포트가 여러 개 보인다. 복잡한 원리는 맞지만, 사람이 매번 외울 구조는 아니다. 그래서 task kugnus:aiops:up과 doctor가 필요하다.

3. task kugnus:aiops:up이 실제로 하는 일

이 명령은 “로컬 AIOps 스택을 켠다”는 압축 명령이다. 정의 위치는 Taskfile.yml의 kugnus:aiops:up task다.

압축 명령이 풀리는 순서 
task kugnus:aiops:up
  -> Taskfile.yml: kugnus:aiops:up
    -> KUGNUS_RESUME_RUN_STRICT_GATE=false bash ./scripts/kugnus-demo-resume.sh
      -> require_oc_login
      -> ensure_rag_backend
      -> ensure_port_forward lightspeed-port-forward 18443:8443
      -> ensure_port_forward action-executor-port-forward 18083:8080
      -> ensure_gateway
      -> ensure_plugin_manifest_state
      -> ensure_console
      -> run_verification
        -> task kugnus:dev:doctor
        -> task kugnus:runtime:smoke
        -> strict Lightspeed gate는 false라서 건너뜀
require_oc_login

oc whoami로 현재 OpenShift 로그인이 살아 있는지 본다.

실패하면 서버 설치를 시도하지 않고 멈춘다. 이때 필요한 행동은 oc login이다.

ensure_rag_backend

scripts/kugnus-rag-pgvector-dev.sh를 통해 로컬 RAG/pgvector 백엔드를 준비한다.

내 PC 개발용 데이터 저장소다. 회사 운영 DB를 새로 만드는 단계가 아니다.

ensure_port_forward

oc -n openshift-lightspeed port-forward svc/lightspeed-app-server 18443:8443 형태로 Lightspeed를 내 PC 포트에 연결한다.

oc -n komsco-ai-dev port-forward svc/komsco-ai-action-executor 18083:8080 형태로 Action Executor도 연결한다.

이것은 회사 서버에 pod를 만드는 행동이 아니라, 이미 있는 서비스를 내 PC에서 접근 가능하게 여는 터널이다.

ensure_gateway

로컬 Gateway가 http://127.0.0.1:18080/healthz에 응답하는지 본다.

없으면 task kugnus:dev:be:execute:rag를 백그라운드로 시작한다.

ensure_console

로컬 OKD 콘솔 브릿지 9000과 플러그인 dev server 9001을 확인한다.

깨져 있으면 scripts/kugnus-okd-console-morning.sh를 repair 모드로 실행한다.

결과물 위치 의미
Gateway localhost:18080 로컬 API 중계 서버. 콘솔 플러그인의 AI 요청이 여기로 온다.
Plugin dev server localhost:9001 OpenShift 콘솔 플러그인 번들을 개발 모드로 제공한다.
Console bridge localhost:9000 Windows 브라우저에서 볼 로컬 OKD 콘솔 화면이다.
Lightspeed 터널 localhost:18443 회사 OpenShift의 Lightspeed 서비스를 로컬 Gateway가 호출하도록 연결한다.
Action Executor 터널 localhost:18083 실행 모드에서 회사 개발 namespace의 executor 서비스를 로컬에서 호출하게 한다.
이 명령이 하지 않는 일

task kugnus:aiops:up은 회사 서버에 OperatorHub 카탈로그를 등록하거나, Subscription을 만들거나, AIOpsInstallation을 설치하는 명령이 아니다. 그런 작업은 aiops:company:publish와 aiops:company:install 계열이다.

4. task kugnus:dev:doctor가 실제로 보는 것

이 명령은 고치는 명령이 아니라 판정하는 명령이다. 정의 위치는 Taskfile.yml의 kugnus:dev:doctor task이고, 실제 실행 파일은 scripts/kugnus-dev-doctor.sh다.

doctor 명령이 풀리는 순서 
task kugnus:dev:doctor
  -> Taskfile.yml: kugnus:dev:doctor
    -> bash ./scripts/kugnus-dev-doctor.sh
      -> Ref stamp: branch, git status, head commit
      -> WSL/toolchain: WSL, native Linux filesystem, sshfs/rclone/kugnus-home 여부
      -> OpenShift context: oc server, oc user, project, required service read
      -> Docker and ports: 9000, 9001, 18080, 18443, 18083, 5173, 5174
      -> Local endpoints: Gateway, console API proxy, plugin chunks
      -> Windows localhost endpoints: curl.exe로 Windows 쪽 접근 확인
      -> Summary: PASS/WARN/FAIL
검사 영역 왜 중요한가 정상 기준
repo filesystem 소스가 SSHFS, rclone, kugnus-home 같은 원격 mount 위에 있으면 빌드와 watch가 느려질 수 있다. WSL ext4/native Linux filesystem, remote mount 없음
port owner 다른 repo의 Vite나 stale process가 같은 포트를 잡으면 브라우저가 엉뚱한 화면을 본다. 9000/9001/18080/18443/18083은 현재 repo 또는 기대 서비스 소유, 5173은 비어 있음
Docker bridge env 콘솔 컨테이너 안에서 WSL IP를 직접 물고 있으면 재부팅 후 깨질 수 있다. host.docker.internal:18080, host.docker.internal:9001
Windows curl WSL 안에서는 되는데 Windows 브라우저에서 안 되는 상황을 잡는다. 18080, 9000, 5174 주요 endpoint가 HTTP 200

5. 로그인 토큰 만료는 왜 생기나

로컬 개발에서는 내 PC의 oc 로그인 토큰으로 회사 OpenShift API를 읽는다. 그래서 SSO/토큰 만료 시간이 지나면 다시 oc login을 해야 한다. 이것은 운영 배포의 정상 형태가 아니라, 로컬 개발 방식의 제약이다.

로컬 개발

내 사용자 토큰으로 회사 API를 읽는다.

토큰이 만료되면 oc login이 필요하다.

브라우저, Gateway, 콘솔 브릿지가 내 PC 포트를 통해 연결된다.

회사 배포

Pod, ServiceAccount, Route, ConsolePlugin이 클러스터 안에서 연결된다.

개발자 개인 토큰으로 계속 붙어 있는 구조가 아니다.

운영자는 배포된 콘솔/서비스를 사용한다.

공부 포인트

“왜 매번 로그인하지?”의 답은 “로컬 개발이 회사 서버 일부를 내 PC에 임시 연결하기 때문”이다. 우리가 바로잡아야 할 것은 사용자가 매번 포트를 외우는 상황이고, 그래서 doctor가 어떤 층이 끊겼는지 이름으로 말하게 만든다.

6. SSH로 회사 계정 로그인을 대체할 수 있나

짧은 답은 직접 대체는 아니다. SSH는 리눅스 서버에 들어가는 통로이고, OpenShift 작업은 결국 api.ocp.cywell.server:6443 같은 API 서버에 토큰, 인증서, 또는 ServiceAccount 권한으로 인증해서 수행된다.

방식 가능 여부 실제 의미 토큰/권한은?
내 PC에서 oc login 현재 방식 WSL에서 바로 회사 OpenShift API에 붙는다. 내 회사 계정의 OAuth token이 필요하다.
회사망 안 서버에 SSH 접속 후 oc 실행 가능 내 PC 대신 bastion/dev 서버에서 명령을 실행한다. VPN, Windows, WSL localhost 문제를 줄일 수 있다. 그 서버 안에서도 oc login, kubeconfig, 또는 승인된 token이 필요하다.
ServiceAccount 또는 CI/CD token 반복 작업에 적합 배포, 상태 조회, 시나리오 테스트처럼 반복되는 작업을 사람 계정 대신 제한된 자동화 계정으로 수행한다. 회사 승인, namespace별 RBAC, 만료/회수 정책이 필요하다.
OpenShift node에 직접 SSH 일반 개발/배포 방법 아님 노드 장애 분석 같은 특수 상황에 가깝다. 애플리케이션 배포는 oc, Operator, Pipeline 경로가 정상이다. 클러스터 관리 정책 영역이다. 개발자가 임의로 택할 우회로가 아니다.
네 질문의 정확한 답

“회사 계정 로그인 대신 SSH로 하면 되지 않나?”는 절반만 맞다. SSH로 회사망 안 개발 서버에 들어가서 그 서버에서 task와 oc를 실행하는 구조는 가능하다. 하지만 그 안의 oc도 OpenShift API 권한이 필요하다. 즉 SSH는 접속 위치를 바꾸는 방법이지, OpenShift 인증을 없애는 방법은 아니다.

SSH형 개발 서버 구조가 있다면 이렇게 보인다 
내 PC
  -> ssh company-dev-host
    -> cd /path/to/ocp-aiops_kugnus
      -> oc whoami
      -> task kugnus:aiops:up 또는 회사 배포 task
        -> OpenShift API는 여전히 token/RBAC로 인증

우리가 나중에 안정화할 수 있는 정상 방향은 두 가지다. 로컬 개발은 SSH bastion/dev 서버 방식으로 옮겨 네트워크 흔들림을 줄이거나, 반복 배포/시나리오 테스트는 ServiceAccount/CI 권한으로 분리하는 것이다. 둘 다 회사 보안 정책 승인이 필요하다.

7. 시나리오 테스트는 원래 어떻게 해야 하나

시나리오 테스트는 “아무것도 만들지 않는 테스트”가 아니다. 실전과 비슷하게 하려면 격리된 테스트 namespace 안에 테스트 pod, 이벤트, 장애 조건을 만들고 AIOps가 감지하는지 봐야 한다.

정상적인 시나리오 테스트 흐름 
테스트 namespace 준비
  -> 예: aiops-scenario-test
    -> 테스트 pod/config/event 생성
      -> AIOps 질문 또는 자동 진단 실행
        -> evidence, action plan, RCA 결과 확인
          -> 테스트 리소스 cleanup
질문 답
테스트 pod를 만드는 게 문제인가? 문제가 아니다. 격리된 namespace와 cleanup 규칙이 있으면 가장 실전적인 길이다.
회사 운영 namespace에 만들어도 되나? 안 된다. 테스트 namespace를 분리해야 한다.
지금 당장 필요한 합의는? aiops-scenario-test 같은 고정 namespace를 회사가 만들어 주거나, 프로젝트 생성 권한을 부여해야 한다.

8. 회사 서버 배포 명령은 따로 있다

README의 회사 서버 배포 흐름은 로컬 실행보다 훨씬 짧다. 하지만 짧아 보이는 이유는 OpenShift가 안쪽 복잡성을 감추고 관리하기 때문이다.

README 기준 회사 배포 흐름 
task aiops:company:check
task aiops:company:publish
task aiops:company:status

# 설치 승인 후에만
task aiops:company:install
task aiops:company:status
명령 실제 수행 서버에 만드는 것 주의
task aiops:company:check oc whoami --show-server가 승인된 회사 서버인지 확인하고 scripts/kugnus-olm.sh package를 실행한다. 서버 설치 리소스 없음 안전한 사전 점검
task aiops:company:publish 서버 확인 후 KOMSCO_AIOPS_APPROVE_PUBLISH=cywell-aiops ./scripts/kugnus-olm.sh publish를 실행한다. 이미지 빌드, OperatorHub 카탈로그 등록/갱신 승인 후 실행
task aiops:company:install 서버 확인 후 KOMSCO_AIOPS_APPROVE_INSTALL=cywell-aiops ./scripts/kugnus-olm.sh install을 실행한다. Subscription, Operator 설치 객체, AIOpsInstallation 및 operand 실제 설치 명령
task aiops:company:status 서버 확인 후 KOMSCO_AIOPS_STATUS_MODE=cluster ./scripts/kugnus-olm.sh status를 실행한다. 없음 읽기 전용 상태 확인

9. 실패하면 어느 층을 보면 되나

실패를 “연결 안 됨”이라고 부르면 매번 다시 헤맨다. 아래처럼 층 이름으로 나눠서 본다.

증상 먼저 볼 것 다음 행동
oc whoami 실패 OpenShift 로그인, VPN, 회사 API 접근 oc login https://api.ocp.cywell.server:6443 후 재실행
서버 주소가 다름 oc whoami --show-server 회사 서버가 아니면 배포/설치 명령은 중단한다.
9000은 뜨는데 AI Gateway proxy 실패 console bridge env, host.docker.internal:18080 task kugnus:aiops:repair 또는 task kugnus:aiops:up
9001 plugin chunk 실패 webpack dev server, plugin manifest task kugnus:aiops:up로 재기동하고 doctor 결과 확인
5173이 잡혀 있음 다른 repo의 stale Vite process doctor가 owner 경로를 보여준다. 현재 repo가 아니면 종료한다.
Windows 브라우저만 실패 curl.exe 결과, WSL/Windows localhost 전달 task kugnus:dev:doctor의 Windows localhost endpoints 섹션을 본다.
Docker가 안 됨 Docker Desktop/daemon Docker Desktop을 켠 뒤 task kugnus:aiops:up 재실행

10. 이번 스터디에서 진짜 익힐 것

지금 목표는 모든 포트를 외우는 것이 아니다. “내가 친 명령이 어느 계층을 건드렸고, 실패하면 어디를 봐야 하는지”를 익히는 것이다.

  • 첫째: 재부팅 후 task kugnus:aiops:up과 task kugnus:dev:doctor만으로 정상 복구되는지 본다.
  • 둘째: doctor가 실패할 때 FAIL 줄의 계층 이름을 읽는다. 포트, Docker, oc, Windows curl 중 어디인지 구분한다.
  • 셋째: 로컬 개발과 회사 배포를 섞지 않는다. kugnus:aiops:up은 로컬 실행, aiops:company:install은 실제 설치다.
  • 넷째: 시나리오 테스트는 테스트 namespace를 써야 한다. 테스트 pod를 만드는 것 자체는 정상이다.
  • 다섯째: 토큰 만료는 “내가 못해서”가 아니라 로컬 개발 연결 방식의 한계다. 운영 배포는 개인 토큰으로 계속 붙는 구조가 아니다.
최종 기준

재부팅 후에도 task kugnus:aiops:up, task kugnus:dev:doctor, 브라우저 localhost:9000/dashboards/aiops 확인까지 1회 루틴으로 끝나면 로컬 실행 공포는 끝난 것이다. 그 다음 공부는 회사 배포와 시나리오 테스트를 분리해서 진행하면 된다.
