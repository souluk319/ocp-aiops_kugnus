Ver.0.1.3 운영 시나리오와 베스트 데모 목표 사이클

이 문서는 Ver.0.1.3에서 작성된 운영 시나리오 계획을 HTML 산출물로 고정하고, 공식 Evidence 기반 Pod restart RCA 목표 사이클을 다음 구현 작업으로 도입하기 위한 기준 문서다.

branch: feat/v.0.1.3 head: 2558dbf mode: Ver.0.1.3 demo read-only only install/deploy: 별도 승인 전 금지

개요

Ver.0.1.2까지는 로컬 개발 콘솔, gateway, 챗봇 UI, evidence/RCA/실행 상태의 기반을 만든 단계다. Ver.0.1.3부터는 UI를 계속 미세 조정하는 대신 실제 운영자가 겪는 사건을 기준으로 기능을 밀어야 한다.

이번 버전은 운영 시나리오 10개를 기준으로 챗봇이 무엇을 물어보고, 어떤 근거를 수집하고, 어떤 RCA 답변과 조치 후보를 보여줘야 하는지 고정한다.

현재 연결 상태

현재 코드상으로는 overview, anomaly, action candidate, status, chat stream의 주요 연결점이 존재한다. 따라서 베스트 시나리오 한 사이클은 완전히 새로 만드는 작업이 아니라, 이미 있는 연결을 한 사건 기준으로 강하게 묶는 작업이다.

운영 시나리오 10개

1. 클러스터 전체 상태 브리핑

ClusterVersion, Operator, Node, Pod, metrics availability를 근거로 정상/주의/위험을 나눈다.

2. ClusterNotUpgradeable 분석

AdminAckRequired, update 가능 여부, operator 상태를 분리해서 업그레이드 차단 원인을 설명한다.

3. Control Plane 메모리 압박

alert와 node metrics를 기준으로 현재 장애와 장애 위험 경고를 구분한다.

4. etcd DB Fragmentation 경고

defrag 자동 실행이 아니라 점검, 백업, 승인, maintenance window 필요성을 분리한다.

5. Pod NotReady 장기화

readiness, image pull, scheduling, resource pressure 후보를 namespace/name/kind와 함께 표시한다.

6. CrashLoopBackOff 원인 분석

waiting reason, restart count, events, logs 필요 여부로 설정 오류/app crash/dependency/resource 후보를 나눈다.

7. ImagePullBackOff / ErrImagePull

image name, pull secret, registry endpoint, event message로 인증/접근/tag 문제를 구분한다.

8. Pending Pod / Scheduling 실패

scheduler event, taint, resource request, PVC, affinity 문제를 확인 순서로 정리한다.

9. 네임스페이스 단위 장애 브리핑

workload readiness, event, alert, service/route를 namespace-local 관점으로 묶는다.

10. 장애 후 조치 후보 검토

RCA context digest, collected/missing evidence, safety mode를 바탕으로 실행 전 제안만 제공한다.

베스트 시나리오

선정: Evidence 기반 Pod restart RCA 공식 기준 문서는 docs/Ver.0.1.3/Evidence_RCA_Scene.md다. 발표 질문은 어제 새벽에 default namespace Pod가 왜 재시작됐어?이며, 이 흐름은 event, grep/log-pattern, metric, snapshot evidence 계획과 RCA Context 구조를 묶는 것을 목표로 한다.

선정 이유

  • 사용자 질문에서 시작해 Tool Plan, Evidence 구조화, RCA Context, Lightspeed handoff 계약까지 한 사이클을 설명할 수 있다.
  • event_tool, grep_tool, metric_tool, snapshot_tool이 모두 등장해 AIOps 관제탑의 차별점을 보여준다.
  • raw log 원문을 노출하지 않고 pattern/digest 기반으로 안전하게 RCA를 구성하는 기준을 보여준다.
  • CrashLoopBackOff 흐름은 공식 목표가 아니라 화면/stream 연결 smoke test로 유지한다.
현재 증거 수준: 브라우저 증거는 공식 질문 staging과 Gateway fallback RCA 답변 렌더링 proof다. 안정적인 Lightspeed 최종 RCA 완료나 실제 default namespace 과거 증적 완전 수집으로 말하지 않는다. 최신 코드에서는 공식 namespace restart collector가 Event, Pod snapshot, previous log pattern probe를 read-only로 시도하고, 없거나 권한이 부족한 증거는 collected/partial/skipped 상태로 드러낸다.

완성 목표 사이클

1 관제탑 진입

대시보드에서 cluster overview와 risk signal을 확인한다.

2 공식 질문 입력

사용자가 "어제 새벽에 default namespace Pod가 왜 재시작됐어?"라고 묻는다.

3 Tool Plan 생성

event_tool, grep_tool, metric_tool, snapshot_tool이 안전한 read-only adapter로 매핑된다.

4 RCA 답변

restart count, waiting reason, event, logs 필요 여부를 근거로 원인 후보를 분리한다.

5 근거 표시

collected/missing evidence와 RCA Context digest를 답변 하단에 붙인다.

6 조치 후보

확인 명령과 점검 순서를 제안하되 apply/delete/patch/scale/exec는 차단 상태로 둔다.

현재 gap

  • anomaly card에서 chat composer로 이어지는 draft prompt 흐름은 연결됐다.
  • chat run, RCA Context, action candidate가 같은 finding id를 end-to-end로 공유하는지 verifier가 검증한다.
  • CrashLoop event evidence는 collected, previous log availability는 raw log 노출 없이 partial evidence로 기록된다.
  • 공식 Evidence RCA 답변 구조는 RCA, 즉시 조치, 재발 방지책, 참고 증적 관점으로 강제되고 verifier가 검사한다.
  • chat stream 완료 후 dashboard refresh callback이 연결되어 관제탑 상태 갱신이 수동 새로고침에만 의존하지 않는다.
  • 10개 전체 시나리오 evaluator는 Ver.0.1.3 기준으로 확장됐고 10/10 pass다.
  • classifier는 Pending Pod / Scheduling 실패를 CronJob activity로 오분류하지 않도록 보정됐다.
  • demo namespace allowlist, mutation disabled, write verb 미실행은 live verifier artifact로 남긴다.

다음 작업

  1. Official Evidence RCA 고정: 공식 질문, Tool Plan, RCA Context, final answer contract가 같은 기준으로 검증되는지 확인한다.
  2. Scenario evaluator 유지: 10개 운영 시나리오 입력, evidence requirement, pass/fail 기준을 회귀 검증한다.
  3. Demo verifier 유지: overview, anomalies, chat stream, action candidates는 화면/stream 연결 smoke test로 계속 pass/fail 리포트를 남긴다.

완료 조건

  • 공식 질문이 Pod restart RCA로 분류된다.
  • Tool Plan에 event_tool, grep_tool, metric_tool, snapshot_tool 대응 항목이 포함된다.
  • 챗봇 답변이 Event, log pattern/digest, metric, snapshot evidence 상태를 포함한다.
  • 근거 부족 항목은 root cause로 확정하지 않는다.
  • 답변 하단에 RCA Context digest와 collected/missing evidence가 표시된다.
  • live verifier에서 event evidence, pod log pattern/availability evidence, snapshot evidence가 stream tool_result로 나온다.
  • live verifier에서 5개 답변 섹션 순서, raw log 미노출, mutation code block 미포함을 확인한다.
  • chat completion 후 dashboard refresh callback이 연결되어 있다.
  • action candidate는 read-only 제안으로 표시되고 실행성 명령은 차단된다.
  • 시연자가 화면을 보며 한 사이클을 3분 안에 설명할 수 있다.
  • 10개 운영 시나리오 evaluator가 10/10 pass이며 negative control도 pass다.
  • 검증 리포트에 같은 finding id 또는 scenario id, RCA digest, collected/missing evidence count, forbidden mutation verbs, mutation disabled 상태가 남는다.
  • CrashLoop 로그 원문은 표시하지 않고, redacted/truncated 기준으로 필요 여부만 설명한다.

하지 않을 것

  • 회사 OCP에 설치/배포하지 않는다.
  • oc apply, oc delete, oc patch, oc scale, oc exec를 실행하지 않는다.
  • 기존 komsco-ai-console-plugin 또는 lightspeed-console-plugin을 교체하지 않는다.
  • UI 미세 수정으로 Ver.0.1.3 기능 작업을 지연시키지 않는다.
  • 근거 없는 추정을 정상 RCA처럼 보여주지 않는다.
