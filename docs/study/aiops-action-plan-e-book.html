KOMSCO AIOps 운영자용 안내서

Action Plan은 어디까지 실행되고 어디에 기록되는가

이 문서는 AIOps 챗봇의 Action Plan을 누르는 사람이 반드시 알아야 할 흐름을 정리합니다. 버튼을 누르면 무엇이 생기고, 검토 기록은 어디서 확인하며, 로컬과 배포판의 저장 방식이 어떻게 다른지 먼저 설명합니다.

한 줄 결론

현재 로컬에서 review_recorded는 Gateway 메모리에 남고, 배포판에서는 OpenShift ConfigMap/komsco-ai-gateway-ledger의 executionRecords.json에 남습니다.

로컬 현재 상태 Gateway 프로세스 메모리. Gateway를 끄면 사라질 수 있습니다.
배포판 상태 OpenShift ConfigMap ledger. Pod 재시작에는 남습니다.
보관 제한 기본 1000건. 넘으면 오래된 기록부터 밀립니다.
운영 완성 gap 장기 감사 보존은 ConfigMap보다 DB 또는 외부 감사 저장소가 더 적합합니다.

목표, 완료 조건, 하지 않을 것

목표 Action Plan 버튼을 누른 뒤 생기는 계획, 승인, 실행 또는 검토 기록의 위치를 운영자가 스스로 확인할 수 있게 한다.
완료 조건 로컬과 배포판에서 review_recorded를 확인하는 명령을 알고, 기록이 언제 사라질 수 있는지 말할 수 있다.
검증 방법 /v1/aiops/status 또는 komsco-ai-gateway-ledger ConfigMap에서 executionRecords를 확인한다.
하지 않을 것 승인 전 클러스터 변경을 하지 않는다. ConfigMap ledger를 장기 감사 DB라고 과장하지 않는다.

Action Plan 전체 흐름

Action Plan은 단순 버튼이 아닙니다. 사용자의 질문이 바로 서버 변경으로 이어지지 않게 중간 단계를 나눠 둔 안전장치입니다.

1. Action Proposal근거를 바탕으로 나온 조치 후보입니다. 아직 실행 계획은 아닙니다.
2. Sealed Action Plan대상, 조치, 검증, 롤백, 승인 조건을 묶은 계획입니다.
3. Approval Decision운영자가 승인 또는 거절한 판단입니다.
4. Execution Record실제 실행 결과 또는 검토 기록입니다. review_recorded도 여기에 속합니다.
사용자 질문
  -> Gateway가 근거 수집
    -> Action Proposal 생성
      -> Action Plan 생성
        -> 운영자 승인 또는 거절
          -> 실행 또는 검토 기록
            -> ExecutionRecord 저장

실행 모드별로 가능한 일

모드 가능한 일 막히는 일
읽기 전용 상태 조회, 원인 분석, 조치 후보 확인 Action Plan 생성, 승인, 실행
실행 가능 Action Plan 생성, 승인, 제한된 typed action 실행 또는 검토 기록 승인 없는 변경, 임의 shell, generic patch
실행 무제한 개발 또는 실험용 확장 모드 서버 정책이 거절하는 작업은 여전히 막힘

읽기 전용에서도 조치 후보를 보는 것은 괜찮습니다. 다만 실제 Action Plan 생성과 승인, 실행은 잠겨 있어야 합니다.

검토 기록은 어디에 남나

안전한 원인 확인 플랜처럼 클러스터를 바꾸지 않는 조치는 실행 결과가 mutation_succeeded가 아니라 review_recorded로 남습니다.

환경 저장소 확인 대상
현재 로컬 실행 Gateway 프로세스 메모리 /v1/aiops/status의 spec.records.executionRecords
OpenShift 배포판 komsco-ai-gateway-ledger ConfigMap executionRecords.json
장기 운영 목표 별도 DB 또는 감사 저장소 필요 아직 제품 gap. ConfigMap은 PoC/초기 운영 저장소로 봐야 합니다.

로컬에서 확인하는 법

로컬 Gateway는 보통 http://127.0.0.1:18080에 떠 있습니다. 인증이 필요한 API이므로 먼저 oc login 상태가 살아 있어야 합니다. 

TOKEN=$(oc whoami -t)
curl -s -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:18080/v1/aiops/status \
| jq '.spec.records.executionRecords[]
  | select(.spec.mutationOutcome.status=="review_recorded")'

최근 기록 하나만 보고 싶으면 아래처럼 봅니다.

TOKEN=$(oc whoami -t)
curl -s -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:18080/v1/aiops/status \
| jq '.spec.records.executionRecords[0]
  | {name:.metadata.name, createdAt:.metadata.createdAt, status:.spec.mutationOutcome.status, planId:.spec.planId}'

현재 로컬 Gateway에 KOMSCO_AI_RECORD_STORE_ENABLED가 없으면 이 기록은 메모리 기록입니다. Gateway를 재시작하면 사라질 수 있습니다.

배포판에서 확인하는 법

배포판에서는 Gateway가 komsco-ai-gateway-ledger ConfigMap에 기록을 씁니다. namespace는 실제 설치 namespace로 바꿔야 합니다. 

NS=<배포네임스페이스>
oc -n "$NS" get configmap komsco-ai-gateway-ledger \
  -o jsonpath='{.data.executionRecords\.json}' \
| jq '.[] | select(.spec.mutationOutcome.status=="review_recorded")'

ConfigMap이 있는지만 먼저 보려면:

NS=<배포네임스페이스>
oc -n "$NS" get configmap komsco-ai-gateway-ledger

Gateway가 record store를 켜고 떠 있는지 보려면:

NS=<배포네임스페이스>
oc -n "$NS" set env deployment/komsco-ai-gateway --list \
| grep KOMSCO_AI_RECORD_STORE

배포판에서 정상이라면 KOMSCO_AI_RECORD_STORE_ENABLED=true, KOMSCO_AI_RECORD_STORE_CONFIGMAP=komsco-ai-gateway-ledger가 보여야 합니다.

언제까지 저장되나

상황 기록 유지 여부
브라우저 새로고침 남습니다.
Gateway Pod 재시작 배포판 ConfigMap 저장이면 남습니다. 로컬 메모리 저장이면 사라집니다.
내 PC 재부팅 배포판 ConfigMap 저장이면 남습니다. 로컬 Gateway만 쓰던 기록은 사라질 수 있습니다.
ConfigMap 삭제 사라집니다.
namespace 삭제 사라집니다.
기록 1000건 초과 기본 설정에서는 오래된 기록부터 밀립니다.

DB 관련 지시는 무엇이었나

공식 산출물의 DB 지시는 주로 Runbook/SOP 검색을 위한 RAG 저장소입니다. 권장안은 PostgreSQL + pgvector입니다.

RAG DB문서, chunk text, embedding vector, ACL metadata 저장. PostgreSQL + pgvector 권장.
Action 기록현재 구현은 ConfigMap ledger. executionRecords.json에 실행 또는 검토 기록 저장.
장기 감사산출물은 감사로그 영구 보존을 요구합니다. 운영 완성판에서는 ConfigMap보다 강한 저장소가 필요합니다.

따라서 “명세서대로 기록을 남긴다”는 방향은 맞습니다. 하지만 “ConfigMap이 최종 장기 감사 DB다”라고 말하면 안 됩니다.

용어를 쉽게 정리

용어 뜻
Gateway 챗봇 뒤에서 OpenShift 조회, 권한 확인, Action Plan 생성, 기록 저장을 담당하는 백엔드 서버입니다.
Action Plan 운영자가 승인하거나 거절할 수 있게 정리된 조치 계획입니다.
검토 기록 클러스터를 바꾸지 않고 “검토했다”는 결과만 남기는 안전한 실행 결과입니다.
Execution Record 실행 결과 또는 검토 결과를 담는 기록 형식입니다. 화면에서는 “실행 기록” 또는 “검토 기록”으로 보여야 합니다.
Audit Ledger 누가 어떤 계획을 승인했고 어떤 결과가 남았는지 모아두는 조치 이력 저장소입니다.

제품 완료 기준

Action Plan 생성 대상, 문제, 조치, 영향, 검증, 롤백, 승인 조건이 보여야 합니다.
승인 전 실행 차단 AI 답변이나 버튼 하나로 바로 클러스터 변경이 일어나면 실패입니다.
검토형 조치 클러스터 변경 없이 review_recorded로 남아야 합니다.
저장 위치 표시 로컬 메모리인지, ConfigMap ledger인지 UI 또는 상세에서 확인 가능해야 합니다.
보관 정책 표시 1000건 제한, ConfigMap 삭제, namespace 삭제 같은 소실 조건을 숨기면 안 됩니다.
운영 장기 보존 고객 납품 기준에서는 별도 DB, 백업, 보존 주기, 마스킹 정책이 필요합니다.
