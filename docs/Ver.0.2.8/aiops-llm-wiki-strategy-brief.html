AIOps for OCP · Ver.0.2.8 Strategy

LLM Wiki는 문서함이 아니라 운영 지식 그래프가 되어야 한다

Palantir의 Ontology 원리와 Obsidian의 네트워크 지식 원리를 AIOps for OCP에 맞게 합쳐, 문서·클러스터 객체·RCA 근거·Action Plan·실행 감사가 하나의 추론 가능한 Wiki가 되는 설계를 고정한다.

1

현재 판단

지금 Wiki는 "RAG 문서 관리"로는 출발했지만, AIOps 제품의 중심 기능이 되려면 "운영 세계를 설명하고 행동으로 연결하는 지식 시스템"이 되어야 한다.

현재 있음

Wiki 메뉴와 문서 UI

OKD embedded와 standalone portal 모두 `위키 문서 관리` 메뉴를 가진다.

현재 있음

RAG 업로드/검색

Gateway에는 `/v1/rag/uploads`, `/v1/rag/search`, ACL, pgvector 기반이 있다.

부족함

운영 객체 그래프

문서가 어떤 Pod, Alert, RCA, ActionPlan과 연결되는지 정식 edge로 고정되어 있지 않다.

현재 Wiki UI는 `sampleKnowledgeDocs`와 local upload state 성격이 강하다. v0.2.8 이후 구현에서는 Gateway Wiki/RAG API를 실제로 호출해야 하며, sample data만으로 운영 화면처럼 보이면 실패다.
결론: v0.2.8은 UI부터 갈아엎는 버전이 아니라, Wiki를 LLM과 Action Plan이 신뢰할 수 있는 지식 그래프로 만드는 계약을 잠그는 버전이다.
2

Palantir에서 흡수할 원리

Palantir Ontology의 핵심은 데이터를 단순히 모으는 것이 아니라, 조직의 운영 세계를 객체, 관계, 액션, 권한으로 모델링하는 것이다. AIP는 이 Ontology 위에서 AI workflow와 agent를 운영 데이터와 실행 체계에 연결한다.

Palantir 개념AIOps 적용제품 의미
Object typeCluster, Namespace, Node, Operator, Pod, Alert, Runbook, ActionPlanLLM이 말하는 대상이 실제 운영 객체와 일치한다.
Link typeaffected_by, remediated_by, verified_by, executed_from문서와 사건과 조치의 연결 이유가 남는다.
Action typerestart, scale, rollback, evict, patchWiki는 실행 조건을 제공하고 실행은 Gateway 정책을 탄다.
Role/permissionOCP RBAC + RAG ACL + 실행 mode볼 수 없는 문서나 객체는 LLM 근거가 될 수 없다.
Functionstale check, risk score, approval condition, rollback condition문서가 운영 의사결정에 들어가기 전 검증된다.
Palantir식으로 해석하면 Wiki의 기본 단위는 파일이 아니라 운영 객체다. 문서는 `MemoryCard`로 변환되고, 그 카드는 OCP 객체와 RCA 근거와 Action Plan을 잇는 traceable object가 된다.
3

Obsidian에서 흡수할 원리

Obsidian의 강점은 사람이 직접 쓰는 Markdown 지식이 내부 링크, 백링크, 그래프, 속성으로 살아 움직이는 것이다. 이 원리는 AIOps Wiki에서도 중요하다. 운영자가 직접 문서를 읽고 고칠 수 있어야 하고, 시스템은 그 문서의 링크와 속성을 해석할 수 있어야 한다.

사람용

Git/Markdown Vault

운영 지식의 원본은 업로드 blob이 아니라 `source_path`, `git_sha`, `frontmatter`, `content_hash`가 남는 Markdown vault여야 한다.

시스템용

YAML Properties

문서 type, owner, 대상 kind, actionTypes, approval, freshness를 machine-readable하게 둔다.

탐색용

Backlink와 Graph

이 문서가 어떤 장애, 어떤 객체, 어떤 조치에서 참조되었는지 거꾸로 볼 수 있다.

근거용

Heading/Block Link

챗봇 답변은 chunk id가 아니라 `source_path#heading^block_id`를 citation으로 보여준다.

병렬 풀스택 에이전트 팀

Agent A

Product/Ontology Architect

객체·링크·액션 vocabulary와 acceptance criteria를 소유한다.

Agent B

Gateway/API Developer

`/v1/wiki/*` API, graph response, stale/gap skeleton을 맡는다.

Agent C

Frontend/Portal Developer

Wiki workbench, graph, document detail, gap queue UI를 구현한다.

Agent D

Assistant/RCA Integration

답변 citation, RCA runbook gate, ActionPlan trace를 연결한다.

Agent E

Ingestion/RAG Developer

Markdown properties, wikilink, object reference, edge suggestion을 만든다.

Agent F

Security/Governance Reviewer

ACL/RBAC, suggested edge 안전성, audit trail을 검수한다.
