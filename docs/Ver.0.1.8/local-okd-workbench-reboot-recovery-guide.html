재부팅 후 아무 연결도 없는 상태에서 시작하는 문서

현재처럼 Kugnus OKD 작업대를 다시 여는 순서

이 문서는 자동화 명령을 외우기 위한 문서가 아닙니다. 어디가 끊겼는지 스스로 확인하고, 그 결과에 맞는 조치를 하기 위한 순서표입니다. 각 단계는 "무엇을 확인하는지", "정상 출력", "실패하면 무엇을 뜻하는지"를 같이 둡니다.

이 문서의 목표

PC가 재부팅되면 로컬에서 켜 두었던 백그라운드 터미널, 포트포워드, Gateway, Docker 콘솔 브릿지 일부가 꺼질 수 있습니다. 회사 OKD 서버가 죽은 것이 아니라, 내 PC에서 회사 OKD를 보기 위해 이어 놓은 통로가 사라진 상태입니다.

목표 상태: 브라우저에서 http://localhost:9000/dashboards를 열었을 때 OKD 콘솔과 Kugnus AI 패널이 보이고, Gateway/RAG/Lightspeed가 응답하는 상태입니다.

이 문서에서는 task kugnus:dev:boot 같은 한 번에 실행하는 명령도 소개하지만, 먼저 각 부품을 사람이 이해할 수 있게 확인합니다. 자동화 명령은 마지막에 시간을 줄이는 도구로만 사용합니다.

작업대 지도

현재 작업대는 한 덩어리가 아니라 여러 연결의 합입니다.

Windows / FortiClient
회사 사설망 10.0.1.230:6443으로 가는 길
WSL Ubuntu
repo, oc, Gateway, 검증 스크립트를 실행하는 작업 공간
Docker
RAG DB와 로컬 OKD 콘솔 브릿지를 담는 컨테이너 공간
OpenShift CLI oc
회사 OKD API에 로그인하고, 서비스 포트포워드를 여는 도구
Gateway 18080
Kugnus AI 화면이 실제 상태와 RAG/Lightspeed를 조회할 때 부르는 Python 서버
Plugin dev server 9001
Kugnus AI 화면 JavaScript를 OKD 콘솔에 제공
Local OKD console bridge 9000
브라우저에 OKD 콘솔을 보여 주는 로컬 중계기

/dashboards가 HTTP 200이라고 해서 전부 정상은 아닙니다. 진짜 기준은 http://localhost:9000/api/kubernetes/version입니다. 이 주소가 200이어야 9000 콘솔이 회사 OKD API까지 실제로 붙은 상태입니다.

SSH와 우회 경로 확인

홈 서버 SSH가 OKD 경로를 우회하는지 의심할 수 있습니다. 현재 확인 결과는 아래와 같습니다.

중요한 결론: "WSL 안에서 SSH 터널이 OKD 경로를 잡고 있지 않다"는 말은 "SSH 터널이 없어서 문제가 생겼다"는 뜻이 아닙니다. 반대로 "현재 OKD API 접속 문제의 주범은 홈 서버 SSH가 아니다"라는 뜻입니다. 회사 OKD API는 api.ocp.cywell.server:6443로 직접 가고, 로컬 작업대는 별도의 개발용 중계기들을 통해 화면과 AI 기능을 붙입니다.

확인 항목 현재 관찰 결과 판단
WSL 안의 SSH 터널 ssh, autossh, sshuttle 프로세스 없음 WSL에서 OKD API를 SSH로 우회하는 흔적 없음
Windows SSH ssh.exe -T -D 49682 Kugnus-Home powershell 실행 중 홈 서버 SSH 연결은 있음. 다만 현재 oc 대상 서버와 다름
Windows 127.0.0.1:6443 ssh.exe가 듣고 있음 위험 지점. OpenShift API 주소를 127.0.0.1:6443으로 쓰면 꼬일 수 있음
현재 OKD API 이름 api.ocp.cywell.server -> 10.0.1.230 회사 OKD는 이 주소로 가야 함
WSL에서 OKD로 가는 경로 10.0.1.230 via 172.29.160.1 dev eth0 WSL이 Windows 게이트웨이를 통해 회사망으로 나감
Windows 회사망 확인 Test-NetConnection api.ocp.cywell.server -Port 6443 성공 FortiClient 쪽 경로가 열리면 OKD API에 접근 가능
Windows portproxy 0.0.0.0:9001 -> WSL 9001 플러그인 dev server를 Windows 브라우저가 볼 수 있게 중계

금지 기준: 이 작업에서는 OpenShift API 서버를 https://127.0.0.1:6443으로 쓰지 않습니다. 그 포트는 현재 홈 서버 SSH 쪽과 엮여 있습니다. 회사 OKD 대상은 항상 https://api.ocp.cywell.server:6443입니다.

직접 확인하는 명령

oc whoami --show-server
getent hosts api.ocp.cywell.server
ip route get 10.0.1.230
powershell.exe -NoProfile -Command "Test-NetConnection api.ocp.cywell.server -Port 6443"

정상 기준은 아래와 같습니다.

https://api.ocp.cywell.server:6443
10.0.1.230 api.ocp.cywell.server
10.0.1.230 via 172.29.160.1 dev eth0 ...
TcpTestSucceeded : True

지금 떠 있어야 하는 백그라운드 구성요소

이것들은 몰래 우회하는 장치가 아니라, 로컬 개발 작업대를 이루는 부품입니다. 브라우저에서는 localhost:9000 하나만 보는 것처럼 보이지만, 실제로는 아래 부품들이 같이 살아 있어야 합니다.

주소 정체 왜 필요한가 재부팅하면
localhost:9000 Docker kugnus-local-console 브라우저에 OKD 콘솔 화면을 보여 주는 로컬 브릿지 컨테이너가 꺼지거나 낡은 토큰을 들 수 있음
localhost:9001 webpack dev server Kugnus AI ConsolePlugin 파일을 OKD 콘솔에 제공 터미널 프로세스라 보통 꺼짐
localhost:18080 Gateway uvicorn Kugnus AI 화면이 RAG, Lightspeed, 진단 API를 부르는 중간 서버 터미널 프로세스라 보통 꺼짐
localhost:18443 oc port-forward to Lightspeed Gateway가 OpenShift Lightspeed에 질문하기 위한 통로 포트포워드 프로세스가 꺼짐
localhost:18083 oc port-forward to Action Executor 실행형 진단 기능이 Action Executor에 닿기 위한 통로 포트포워드 프로세스가 꺼짐
localhost:15432 Docker kugnus-rag-pgvector 고객 문서와 운영 문서를 검색하는 RAG DB Docker 상태에 따라 살아 있거나 꺼질 수 있음

따라서 아침 복구의 핵심은 "SSH 터널을 찾는 것"이 아닙니다. 회사망, oc 로그인, Docker, Gateway, 포트포워드, 9000 콘솔 브릿지를 순서대로 확인하는 것입니다.

0. 작업 위치 확인

먼저 repo 위치로 이동합니다.

cd ~/cywell/ocp-aiops_kugnus
pwd

정상 출력:

/home/kugnus/cywell/ocp-aiops_kugnus
이 repo에는 Taskfile.yml, scripts/, Gateway, ConsolePlugin이 모두 들어 있습니다. 다른 위치에서 명령을 치면 같은 이름의 포트나 설정을 보고도 엉뚱하게 판단할 수 있습니다.

1. 회사망이 열렸는지 확인

Windows에서 회사 OKD API 포트가 열리는지 봅니다.

powershell.exe -NoProfile -Command "Test-NetConnection api.ocp.cywell.server -Port 6443"

정상 출력에서 봐야 할 줄:

RemoteAddress    : 10.0.1.230
RemotePort       : 6443
TcpTestSucceeded : True
결과 뜻 조치
True Windows에서 회사 OKD API까지 길이 열림 다음 단계로 이동
False 또는 timeout FortiClient/VPN/회사망 경로 문제 FortiClient 로그인 후 다시 실행

2. WSL의 oc 로그인을 확인

터미널이 어느 OKD 서버를 보고 있는지 확인합니다.

oc whoami --show-server
oc whoami
oc project --short

정상 출력 예시:

https://api.ocp.cywell.server:6443
admin
gpu-test-kugnus
결과 뜻 조치
Unauthorized 터미널의 OpenShift 토큰이 만료됨 oc login을 다시 수행
서버가 127.0.0.1:6443 홈 서버 SSH 또는 다른 로컬 터널을 보고 있을 수 있음 회사 서버로 다시 로그인
서버가 api.ocp.cywell.server:6443 회사 OKD 대상이 맞음 다음 단계로 이동

다시 로그인할 때:

oc login --token=토큰값 --server=https://api.ocp.cywell.server:6443

3. Docker가 살아 있는지 확인

로컬 컨테이너를 담는 Docker를 확인합니다.

docker ps

정상이라면 표가 나옵니다. 재부팅 직후에는 일부 컨테이너가 없거나 꺼져 있을 수 있습니다.

보면 좋은 컨테이너 역할
kugnus-rag-pgvector RAG 문서 검색용 로컬 DB
kugnus-local-console localhost:9000 OKD 콘솔 브릿지
Docker가 안 켜져 있으면 RAG DB와 9000 콘솔 브릿지가 올라올 수 없습니다. Docker Desktop부터 켠 뒤 다시 확인합니다.

4. RAG DB를 준비

문서 검색용 pgvector DB를 켭니다.

bash scripts/kugnus-rag-pgvector-dev.sh

정상 출력 예시:

RAG pgvector dev backend is ready.
Container: kugnus-rag-pgvector
DSN env: KOMSCO_AI_RAG_BACKEND_URL=postgresql://komsco_aiops@127.0.0.1:15432/komsco_aiops
이 단계는 OKD 콘솔 자체와는 별개지만, Kugnus AI가 고객 문서와 운영 문서를 검색하려면 필요합니다.

5. Gateway와 OKD 서비스 터널을 준비

Gateway는 Kugnus AI 화면의 중간 서버입니다. 이 명령은 Gateway를 켜고, Lightspeed와 Action Executor로 가는 로컬 포트도 준비합니다.

Gateway를 실행합니다.

task kugnus:dev:be:execute:rag

이 명령은 터미널 하나를 계속 차지할 수 있습니다. 작업 중에는 이 터미널을 닫지 않습니다.

다른 터미널에서 확인합니다.

curl http://127.0.0.1:18080/healthz
curl -k https://127.0.0.1:18443/readiness
curl http://127.0.0.1:18083/healthz

정상 출력:

{"status":"ok"}
{"ready":true,"reason":"service is ready"}
{"status":"ok"}
포트 정체 안 되면
18080 Kugnus Gateway Gateway가 안 켜졌거나 터미널이 꺼짐
18443 OpenShift Lightspeed 로컬 터널 oc 로그인, VPN, Lightspeed 서비스 접근 확인
18083 Action Executor 로컬 터널 komsco-ai-dev namespace 서비스 접근 확인

6. 플러그인 dev server 확인

OKD 콘솔이 읽어 갈 Kugnus AI 화면 파일을 확인합니다.

curl -sS -o /dev/null -w '%{http_code}\n' \
http://127.0.0.1:9001/api/plugins/komsco-ai-console-plugin-kugnus/plugin-manifest.json

정상 출력:

200
결과 뜻 조치
200 Kugnus AI 화면 파일 제공 중 다음 단계로 이동
000, timeout, connection refused 9001 dev server가 꺼짐 다음 9000 콘솔 복구 명령이 필요하면 9001도 같이 띄움

7. Local OKD console 9000 확인

껍데기가 아니라 실제 API 연결을 확인합니다.

curl -sS -o /dev/null -w '%{http_code}\n' \
http://localhost:9000/api/kubernetes/version
결과 뜻 조치
200 9000 콘솔이 회사 OKD API까지 실제로 붙음 브라우저를 열면 됨
401 또는 403 9000 컨테이너가 낡은 oc 토큰을 들고 있음 task kugnus:dev:console:repair
502, 000, timeout 9000 컨테이너에서 회사 OKD API로 못 나감 FortiClient, 회사망, oc whoami부터 다시 확인

9000을 재생성할 때:

task kugnus:dev:console:repair
localhost:9000/dashboards는 HTML만 줄 수 있습니다. 그래서 이 문서에서는 항상 /api/kubernetes/version을 진짜 기준으로 씁니다.

8. 브라우저에서 작업대 열기

마지막에 브라우저를 엽니다.

http://localhost:9000/dashboards

화면이 이상하면 먼저 강력 새로고침을 합니다.

Ctrl + F5

브라우저 탭은 이전 세션의 JavaScript나 WebSocket 상태를 잡고 있을 수 있습니다. 서버 쪽 확인이 모두 200인데 화면만 이상하면 새 탭 또는 강력 새로고침으로 갈라 봅니다.

최종 체크 묶음

아래 명령들이 모두 정상이어야 현재 작업대가 열린 상태입니다.

powershell.exe -NoProfile -Command "Test-NetConnection api.ocp.cywell.server -Port 6443"
oc whoami --show-server
oc whoami
docker ps
curl http://127.0.0.1:18080/healthz
curl -k https://127.0.0.1:18443/readiness
curl http://127.0.0.1:18083/healthz
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9001/api/plugins/komsco-ai-console-plugin-kugnus/plugin-manifest.json
curl -sS -o /dev/null -w '%{http_code}\n' http://localhost:9000/api/kubernetes/version

모두 정상이라면 브라우저에서 http://localhost:9000/dashboards를 엽니다. 이때부터는 자동화 명령을 써도 됩니다. 자동화는 위 순서를 대신 실행하는 도구일 뿐입니다.

도움 요청할 때 이렇게 보내기

다음부터는 "안 열려" 대신 아래 형식으로 보내면 바로 원인을 좁힐 수 있습니다.

회사망: Test-NetConnection True
oc: admin / https://api.ocp.cywell.server:6443
Docker: docker ps 됨
18080: 200
18443: 200
18083: 200
9001 manifest: 200
9000 api: 401
브라우저 증상: dashboards는 흰 화면

위 예시는 바로 이렇게 판단합니다.

9000 api: 401이므로 9000 콘솔 브릿지가 낡은 토큰을 들고 있습니다. 조치는 task kugnus:dev:console:repair입니다.

자동화 명령은 언제 쓰나

위 단계를 이해한 뒤, 시간을 줄이고 싶을 때 씁니다.

명령 언제 쓰나 내부적으로 보는 것
task kugnus:dev:console:morning 9000 콘솔만 의심될 때 회사 API, oc, 9000 API, 9001 manifest
task kugnus:dev:boot PC 재부팅 후 전체 작업대를 다시 열 때 RAG, Lightspeed, Action Executor, Gateway, 9000, runtime smoke
task kugnus:dev:doctor 현재 상태를 진단만 하고 싶을 때 도구, oc, Docker, 포트, 로컬 endpoint

자동화 명령이 실패하면 그 출력에서 어느 단계가 실패했는지 먼저 봅니다. 그 다음 이 문서의 판정표로 돌아오면 됩니다.
