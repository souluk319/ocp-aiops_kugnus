RCA AIOps RAG를 Memory Card Layer로 고도화한다

Memora 기사와 Microsoft 원본 저장소의 핵심을 우리 시스템에 맞게 해석한 설계 브리핑이다. 결론은 GraphRAG 전면 전환이 아니라, 기존 RAG 위에 검색 표현과 원문 저장을 분리하는 RCA Memory Card Layer를 얹는 것이다.

현재 판단

Memora의 핵심은 원문과 검색 표현을 분리하는 것이다. 이 개념은 RCA AIOps RAG에 직접 적용 가치가 있다. 다만 라이브러리를 그대로 넣는 방식보다, 표현 구조를 우리 Gateway와 RAG 스키마에 흡수하는 것이 더 안전하다.

Memora에서 가져올 핵심

기사와 README가 공통으로 강조하는 구조는 세 가지다.

Memory value 원문과 세부 정보를 보존한다. 검색 인덱스에 직접 넣기보다, 검색 후 반환할 실제 근거로 둔다.
Primary abstraction 각 memory가 무엇에 관한 것인지 나타내는 대표 요약이다. 검색, 병합, 중복 제거의 기준이 된다.
Cue anchors 같은 memory로 들어가는 여러 검색 단서다. 장애명, 에러코드, 증상 표현, 리소스명을 묶는다.

우리 시스템에서는 원문 런북과 RCA 보고서를 Memory value로 보존하고, 장애 분석용 Primary abstraction과 Cue anchors를 별도로 만들어 검색 품질을 끌어올린다.

왜 AIOps RCA에 맞는가

OpenShift 장애 질문은 표현이 계속 바뀐다. 같은 문제라도 사용자는 OOMKilled, ExitCode 137, 메모리 초과, Pod 재시작, CrashLoopBackOff처럼 다르게 말한다. raw chunk만 임베딩하면 이 표현 차이에 약하다.

{
  "primary_abstraction": "Pod OOMKilled 발생 시 memory limit, node pressure, 최근 배포 변경, heap 설정을 확인한다.",
  "cue_anchors": [
    "OOMKilled",
    "ExitCode 137",
    "memory limit exceeded",
    "container killed",
    "pod restart",
    "CrashLoopBackOff",
    "메모리 초과"
  ],
  "memory_value_ref": "runbook:ocp-oomkilled#diagnosis"
}

이 구조는 질문 표현과 문서 표현이 달라도 같은 RCA memory에 도달하게 만든다.

RCA 처리 흐름

  1. 질문을 task type, entity, symptom으로 정규화한다.
  2. Primary abstraction과 cue anchors에서 관련 Memory Card를 찾는다.
  3. Memory Card가 가리키는 원문 chunk와 live OCP evidence를 확장한다.
  4. tool_hints를 Tool Plan으로 변환한다.
  5. safety_class와 policy를 적용해 mutation을 차단하거나 승인 대상으로 보낸다.
  6. RCA JSON에 cause candidates, evidence refs, next checks를 채운다.

GraphRAG와 파인튜닝의 위치

레이어역할

파인튜닝은 지식 주입용이 아니라, 나중에 Tool Plan JSON 안정화, RCA JSON 누락 감소, task type 분류 보정에 제한적으로 쓴다.

응용 활용 범위

OCP 장애 RCA CrashLoopBackOff, ImagePullBackOff, OOMKilled, Pending, Route 장애를 증상에서 evidence 기반 RCA로 연결한다.
폐쇄망 설치/교육 설치 runbook을 Memory Card로 바꿔서 확인 명령, PASS 기준, 롤백 기준으로 접근한다.
발표/시연 질문, 검색된 Memory Card, 원문 chunk, live evidence, RCA JSON 흐름을 보여준다.
고객별 LLM Wiki 고객 SOP, 장애 이력, 벤더 문서, 정책을 factual/procedural/episodic/policy memory로 정리한다.
Multi-agent handoff 분석 agent, 실행 계획 agent, 교육 문서 agent가 같은 memory card를 공유한다.
운영 품질 평가 질문이 올바른 card를 찾는지, card가 원문 chunk와 evidence를 제대로 연결하는지 측정한다.

Ver.0.1.9 작업 제안

  1. TEI 502를 해결하고 기존 hashing-bow-v1 chunk를 재인제스트한다.
  2. 실제 OCP Runbook/SOP/RCA corpus를 최소 10개 확보한다.
  3. 오프라인 Memory Card 생성기를 만든다.
  4. raw chunk only, memory card only, hybrid card + chunk 검색을 비교한다.
  5. Memory Card의 evidence_types, tool_hints, safety_class를 RCA JSON과 Tool Plan에 연결한다.
  6. GraphRAG는 resource relation link가 쌓인 뒤 붙인다.
Ver.0.1.9에서 하지 않을 것: Memora production dependency 직접 도입, GraphRAG 전면 교체, TEI 502 상태 재인제스트, GRPO 학습, LoRA/SFT, 운영 mutation 자동 실행.

최종 결론

Memora에서 가져올 것은 라이브러리 자체보다 표현 구조다. RCA AIOps RAG는 원문 chunk 검색만으로 끝내지 않고, Runbook, SOP, RCA, OCP evidence를 Memory value로 보존하며, Primary abstraction과 Cue anchors를 별도 검색 표현으로 만들어 Tool Plan, Evidence 판단, RCA JSON 생성으로 연결해야 한다.

지금 우리에게 필요한 것은 모델을 더 똑똑하게 만드는 것보다, 모델이 찾아야 할 운영 기억을 더 정확하게 표현하고 검증 가능하게 연결하는 것이다.
