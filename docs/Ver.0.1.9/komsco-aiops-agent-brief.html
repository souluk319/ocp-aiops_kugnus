Section 01

개요 — KOMSCO AIOps란

한국조폐공사 OCP 클러스터의 운영 지능화를 위한 AI 에이전트 플랫폼. OpenShift Console에 플러그인 형태로 통합되어, 운영자가 자연어로 장애를 질의하면 증거를 수집하고 원인을 분석해 조치 후보까지 제시합니다.

🎯
핵심 목표

운영자가 "왜 이 Pod가 재시작됐어?" 같은 자연어 질문을 하면, OCP API → 로그 → 이벤트 → 런북을 자동으로 뒤져 근거 기반 RCA 답변을 생성한다.

🔒
폐쇄망 설계

외부 인터넷 없이 회사 OCP 클러스터 내에서 완전히 동작. OpenShift Lightspeed (OLS)를 최종 답변 생성 레이어로 사용하며 파인튜닝 없이 고유 운영 데이터를 RAG로 반영한다.

🛡️
Safety-First

기본 동작은 read-only. oc apply / delete / exec 같은 변경 명령은 명시적 승인 모드(execute)에서만 허용. 민감 정보 자동 redact, RBAC 기반 ACL 적용.

🔌
Console Plugin 통합

OpenShift Dynamic Console Plugin으로 구현. 별도 UI 없이 OCP 콘솔 안에서 채팅 패널, 증거 패널, 대시보드, 조치 후보 패널이 함께 제공된다.

Section 04

RAG 현황 진단

v0.1.7에서 semantic embedding 인프라를 갖췄지만, 실제 운영 데이터를 보면 두 가지 근본 문제가 확인됩니다.

⚠️
임베딩 서비스 상태 (2026-06-30 기준) 회사 TEI 임베딩 서비스(tei.cywell.co.kr)가 HTTP 502로 응답 불가 상태. 이에 따라 개인 홈서버의 EmbeddingGemma 서비스를 임시 연결해 운영 중. 단, EmbeddingGemma의 벡터 차원이 기존 설정(1024차원)과 다를 수 있으므로 인제스트 전 차원 일치 여부를 반드시 확인해야 합니다.
현재 RAG DB 상태
항목값평가
총 청크 수 11개 매우 부족
문서 수 9개 미비
임베딩 모델 hashing-bow-v1 비의미적
벡터 차원 (설정) 1024 EmbeddingGemma 확인 필요
TEI 서비스 HTTP 502 다운
대체 임베딩 EmbeddingGemma (홈서버) 차원 검증 필요
실제 OCP 런북 0개 없음
hashing-BOW-v1이란?

토큰을 SHA256으로 해싱해서 64개 버킷에 분산하는 방식. 의미(semantic)를 전혀 반영하지 않는다. 

# 검색 결과 비교
쿼리:   "메모리 부족으로 Pod 종료"
hashing-BOW: ❌ OOMKilled 런북 못 찾음
semantic:    ✅ "OOMKilled · Java heap OOM" 런북 반환
💡
영향 범위 현재 RAG 검색 결과는 키워드 정확 일치 수준. "OOMKilled"를 검색하면 OOMKilled가 정확히 들어있는 청크만 찾고, "메모리 초과"나 "Java heap" 같은 동의 표현은 못 찾는다.

Section 05

v0.1.9 계획 — RAG 스터디 & 실험

v0.1.8까지는 기능 구현에 집중했다면, v0.1.9는 시스템에 대한 이해도를 높이는 단계입니다. 오픈소스 RAG 관련 프로젝트를 직접 검토하고 실험해보면서, 현재 시스템에 어떻게 응용할 수 있을지 풍부한 인사이트를 쌓는 것이 목표입니다.

🔬
실험 목적 아래 두 오픈소스를 스터디 겸 테스트 목적으로 검토합니다. 현재 시스템에 즉시 적용하는 것이 아니라, 각 프로젝트의 구조와 접근법을 이해하고 AIOps RAG 시스템에 어떤 아이디어를 가져올 수 있는지 탐색하는 과정입니다. 실험 결과에 따라 기능 고도화 방향을 구체화할 예정입니다.
참조 레포지토리
🗂️

OpenKB — Vectify AI

github.com/VectifyAI/OpenKB

AI 기반 오픈소스 지식 베이스 시스템. 문서 → 구조화 지식 변환, 엔티티 추출, 벡터 + 그래프 하이브리드 검색을 지원. 폐쇄망 환경에 자체 호스팅 가능.

실험 방향 OpenKB가 문서에서 엔티티와 관계를 어떻게 추출하고 구조화하는지 직접 살펴본다. OCP 런북 샘플을 투입해 어떤 형태의 지식 그래프가 만들어지는지 확인하고, 현재 flat 청크 검색과 비교했을 때 어떤 차이가 있는지 경험적으로 파악하는 것이 목적.
🧠

Memora — Microsoft

github.com/microsoft/Memora

LLM을 위한 에피소딕 메모리 시스템. 과거 인터랙션/사건을 구조화된 메모리로 저장하고, 새로운 질문이 들어오면 유사한 과거 기억을 검색해 퓨샷 컨텍스트로 주입. 재학습 없이 LLM이 "과거에 비슷한 장애를 어떻게 해결했는지"를 참조 가능.

실험 방향 Memora가 과거 사건을 메모리로 저장하고 검색하는 방식을 분석한다. AIOps 장애 이력 데이터에 적용했을 때 어떤 형태로 메모리가 구성되는지, 유사 장애 검색 품질이 어느 수준인지 실험을 통해 파악하는 것이 목적.

📌
실험 방향 각 접근법을 독립적으로 테스트한 뒤, 현재 AIOps 시스템의 특성(OCP 중심, 폐쇄망, 소규모 코퍼스)과 어떻게 맞는지 이해도를 쌓는 것이 목표입니다. 결과에 따라 기능 고도화 방향을 구체화합니다.
관계 경로 예시 — "webapp Pod 접속 장애 원인" 
# Structured KB (OpenKB) 적용 시 경로 탐색 예시
Route            ──exposes──▶  Service
Service          ──selects──▶  Pod (webapp-deploy-*)
Pod              ──caused_by──▶ Event: ImagePullBackOff
ImagePullBackOff ──references──▶ Secret: registry-auth
Secret           ──explained_by──▶ Runbook: "이미지 풀 인증 실패 대응"
Runbook          ──action──▶  "pull-secret 재생성 후 Deployment 재시작"
🔬
이런 경로 구조가 실제로 추출 가능한가? OpenKB 실험을 통해 OCP 런북 문서로부터 이런 관계 경로가 어느 수준으로 자동 추출되는지 직접 확인해볼 예정입니다. 결과에 따라 AIOps 시스템에 어떻게 응용할지 판단합니다.

Console Plugin으로서 AIOps가 어떻게 동작하는지, Scenario 11 시연을 통해 검증된 내용을 정리합니다.

Console Plugin 통합 흐름
단계동작
